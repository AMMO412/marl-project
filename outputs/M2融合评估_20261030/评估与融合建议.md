**结论：以 D:/Desktop/MARL项目/planning_middle_demo 为主工程合理。可借鉴 M2 的消息入口、数据结构分层及导出组织方式；保留主工程的运行协调、反馈轨迹和工作台。不能据现有示例判定哪边算法或执行效果更好。**

## 3. 不能直接合并的语义

### 能力与资源

M2 的 capabilities 是能力代码到等级；主工程的载荷、传感器标签、效率等是另一套暂定画像。能力等级 2 不等于载荷 2，也不代表两个单位工作量。先建立字段词典和来源，不自动推算等级转换。

M2 的 endurance_s 是累计使用时间限制，energy 是模型代价；主工程 battery 是模型电量。三者不能直接写入同一个 battery 字段，也不能据数值大小比较谁更节能。

### 时间与坐标

M2 使用计划相对秒数及平面尺度 cell_size_m；主工程协议仍标 demo_sim_steps，历史场景存在缩放，新城市场景 scale=1。即使坐标恰好数值相同，也必须声明单位和坐标变换。

建议在通用演示中先明确世界坐标与展示坐标、仿真步与秒的转换；保留 source_time_unit、source_coordinate_frame。不要全局把 *_s 改名后视作单位已统一。墙钟 issued_at、计划相对时间、仿真时钟分别保留。

### 指令与状态

主工程 command 是作业尝试，M2 command 是速度段。需要“作业尝试—速度段”的父子映射，而不是直接复用命令 ID。主工程的协调器继续拥有运行状态；输入适配与计划预览只产生数据，不写运行终态。

M2 execution.py 的速度命令编号由 CMD-00001 起生成；coordinator.plan() 更换计划后重建反馈日志。跨版本旧反馈隔离需要另行验证，不能仅凭 plan_version 字段存在就认为已解决。

### 证据与展示

计划、按计划插值、模拟反馈轨迹和外部实测是不同数据来源。统一报告时必须保留来源标签；导入计划不得填充“已执行成功”，也不能将计划轨迹拼接成反馈轨迹。

主工程报告、源场景与运行快照存在版本差异。例如当前 scenarios/asl_city.json 与 outputs/asl_city/report.json 的平台和窗口信息不完全相同。因此比较必须使用每轮保存的 scenario.json 和 manifest，不引用当前源码场景替代历史输入。

## 4. 值得吸收什么，保留什么

优先吸收的通用设计：

1. **输入信封与资源表分离**：消息版本、来源、消息身份、任务几何、依赖校验；可先做只读导入和字段错误报告。
2. **原始对象与派生对象分层**：保留父任务、子项、分配和输出之间的关联，报告可以追溯生成过程。
3. **离线输出组织**：JSON 保存完整结构，CSV 明确为字段子集，Markdown 用于人工审阅；同一轮产物用 manifest 关联。
4. **模块边界**：将解析、转换、报告等通用功能独立，不复制整套业务规划器。

主工程继续保留：CoordinatorV2 运行协调、运行内身份与取消/确认机制、原始反馈日志、工作台、现有历史结果及已实现的通用运动替身。保留不代表这些模块已通过本轮完整审查。

暂不整体移植 M2 的 scheduler/coordinator/execution；它们承担的职责与现有主链重叠。通用输入适配成熟前也不同时替换求解器、运动模型和完成判定，否则无法归因变化来自哪里。

首个里程碑调整为“基于已确认规范的输入输出字段表、适配边界、通用契约校验及成对样例”。先在无武器中性任务验证。工作台改造、算法比较与真实平台联调放在接口里程碑之后；通过静态契约校验不等于外部平台已接通。

初期新增文件可集中于独立 adapters/ 与测试样例目录；具体字段与文件名待规范原文逐条核对后确定。不要把 M2 整体覆盖到 planning_middle_demo，也不在并行工作目录切换分支或重置他人修改。

## 6. 如何公平判断“哪个更好”

先分开比较两个问题：一是通用计划质量，二是运行链的健壮性。离线规划器不能因为不处理取消确认就直接判定算法差；运行链也不能因为有动画就判定规划质量高。

| 对比组 | 固定条件 | 查看指标 |
| --- | --- | --- |
| 正常中性任务 | 同平台、同参数、同地图、同任务窗口、同执行模型 | 完成率、实际完成时长、行驶距离、约束违反数 |
| 包含障碍的检查点移动 | 同几何、机器人尺寸及地图分辨率 | 是否可达、终点误差、碰撞记录、失败原因 |
| 协同集合 | 同参与数量、起点、目标与到达容差 | 到达时间差、等待时间、资源占用是否重叠 |
| 反馈异常 | 重复、乱序、旧尝试、跨运行反馈 | 错误反馈接受数、运行状态是否受污染 |
| 打包与复现 | 新输出目录、明确 Python 版本、输入快照 | 缺文件数、可复现结果、日志与报告一致性 |

确定性场景先用固定样例检验；有随机性时预先固定一组种子并成对运行，报告分布、失败与边界样例。不要只挑最好的一次，也不把运行耗时差异当作任务完成时长差异。

本轮不提供算法名次。M2 现有两平台离线示例与主工程混合平台的分阶段模拟，输入和完成定义都不同，原始秒数没有公平的排名意义。
