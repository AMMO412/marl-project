# 两个工程的融合与对比（2026-10-30）

## 结论

以你的 `MARL项目`（`planning_middle_demo`，下称“基座”）为基础，新增
`planning_middle_demo/interop/` 作为 **1028 4.1/4.2 统一接口 + 中性任务规划内核**，
把 M2 的契约、分解、能力闸门、协同组匈牙利、三目标与风险 A* 并进来；基座的
运行协调器、反馈、行为层、工作台、历史结果都没有改动。

融合后不是“谁覆盖谁”，而是三层分工：

| 层 | 归属 | 职责 |
| --- | --- | --- |
| 统一接口/规划 | `interop/` | 4.1 严格解析 → 4.2 计划/指令 → 报表/manifest；支持与 M2、基座对比 |
| 运行协调 | 基座 `CoordinatorV2` / `mock_fleet` | 指令下发、反馈核对、取消/确认/重试、工作台回放 |
| 任务动作 | 基座 `behaviors.py` / `city_nav.py` | 巡逻、侦察、封控、坚守的到位动作与避障运动 |

一句话：**规划与接口用统一层，运行与展示继续用基座；M2 作为只读对比后端，源码未改。**

运行对接（统一层已接进 `CoordinatorV2`、工作台与基座入口）见
[运行对接_20261030.md](运行对接_20261030.md)。

```powershell

  --formation interop/scenarios/patrol_checkpoint.formation.json --out ..\outputs\interop_demo\patrol
```

## 2 吸收了 M2 的什么

| M2 长处 | 落点 | 说明 |
| --- | --- | --- |
| 4.1 消息信封与编成表分离、逐字段校验 | `interop/message.py` | 比 M2 更严：只接受 `schema_version=0.3`，0.1/0.2 明确拒绝 |
| 父任务→子任务→分配→指令的分层 | `model.py` / `templates.py` / `scheduler.py` | 保留可追溯的父子关系 |
| 能力闸门 + 拒绝原因 | `gate.py`、`unassigned[]` | 不静默丢任务 |
| 协同组“槽位×平台”匈牙利 | `assignment.py` | 一对一最优，平台可多于槽位 |
| 三目标（时效/风险/能耗） | `cost.py` | 系数仍是演示值，报告保留标签 |
| 风险感知栅格 A* | `routing.py` | 8 邻域 + octile，比 M2 的 4 邻域路径更短 |
| 结构化冲突/未分配 | `validate.py` | 补了“路径穿禁入区”检查 |
| JSON 全量 + CSV 字段子集 + Markdown | `output.py` | 补 manifest（输入/输出 SHA256） |
| SDF 显式盒体 → 障碍 | `sdf_scene.py` | 场景生成工具使用 |

## 3 同轮修正的 M2 问题

这些不是“重写”，而是在吸收时修掉的可复现问题：

1. **区域/路线拆分不读 `max_units`**：M2 会拆出超过兵力上限的槽位。对比中
   `patrol_checkpoint` 的 T1/T2 上限 1 台，M2 用了 3 台/2 台；`area_recon`
   的 T1 上限 3 台，M2 用了 4 台。统一层按上限截断。
2. **`simultaneous_arrival` 只保证同组不同平台**：M2 不保证同时开始。统一层
   把所有槽位对齐到同一开始时刻（对外可解释为同时到达）。
3. **协同组匹配后平台可能被别的任务抢走**：统一层在组内槽位全部处理完前
   预留平台，且失败也会释放，不会永久占住。
4. **父任务目标在禁入区**：M2 只检查子任务目标；统一层对父任务目标同样拒绝，
   整组槽位报 `NO_GO`。

## 4 同输入对比结果

样例：4 组中性场景（巡逻+坚守、区域侦察、封禁+检查点、能力缺口负例），
同一份 4.1 输入、同一份障碍、同一套审计（时间窗、平台重叠、能力、目标禁入区、
路径穿禁入区、依赖、兵力上限）。完整表见 [compare.md](compare.md)。

关键数字（timeliness，单位秒）：

| 场景 | unified | 基座 planner_v2 | M2 | 硬违规（u/b/m） | 能力缺口（u/b/m） |
| --- | ---: | ---: | ---: | --- | --- |
| area_recon | 183.6 | **177.0** | 182.1 | 0 / 0 / 1 | 0 / 1 / 0 |
| mixed_inspection | **210.0** | 291.0 | 210.0 | 0 / 0 / 1 | 0 / 3 / 0 |
| patrol_checkpoint | 300.0 | **292.0** | 300.0 | 0 / 2 / 2 | 0 / 2 / 0 |
| capability_gap（负例） | 130.2 | 198.0 | 130.2 | 0 / 0 / 0 | 0 / 3 / 0 |

规划耗时：unified 冷启动约 6–7 s（首次建栅格），同场景后续 0.02–0.3 s；
基座 0.02–0.2 s；M2 约 13–16 s。

解读：

- **只看 makespan，基座并不总是更慢**：`area_recon` 177 s 比统一层快 6.6 s，
  `patrol_checkpoint` 292 s 比统一层快 8 s。但基座同时把 HLD 任务派给了
  `HLD=0` 的平台（本场景 1–2 个能力缺口），并且不检查窗口下界（292 s 的计划
  里 112 s 就开工，早于 120 s 窗口）。所以这个“更快”是省略约束换来的。
- **M2 与统一层 makespan 接近**，多数场景相同；M2 更快一点的地方（area 182.1）
  伴随 1 个兵力上限违规与 1 组协同未对齐。
- **风险目标**（unified vs M2）：统一层 4/4 场景把模型风险压到 0；M2 也都到 0，
  但仍有兵力上限违规/协同未对齐。完整表见
  [risk compare](../interop_risk_20261030/compare.md)。
- **能力缺口是契约差异**：基座 `middle-demo/v2` 没有 4.1 的能力编码，只有
  payload/sensor/altitude；这不是算法错误，而是接口没对齐。统一层的价值首先
  在这里。

## 5 分维度结论：谁更好

| 维度 | 更好的一方 | 依据 |
| --- | --- | --- |
| 4.1/4.2 契约完整性 | **统一层** | 只收 0.3；能力、上限、窗口上下界、协同、路径都可校验；0 硬违规 |
| 规划速度 | **基座**（毫秒级） | 统一层冷启动 6–7 s（首次建栅格）、同场景后续 0.02–0.3 s；M2 13–16 s；基座是滚动时域小算例，量级不同 |
| makespan | 视场景 | 基座在 2/4 场景更短，但以省略能力/窗口约束为代价；统一层与 M2 基本持平 |
| 路径与避障 | **统一层 / M2** | 两者都有 A* 路径；基座计划层没有路径几何 |
| 协同同时性 | **统一层** | 统一开始；M2 只是标签；基座按 crew 同 start 但没有能力语义 |
| 兵力上限 | **统一层** | 拆分不超 `max_units`；M2 超限 |
| 场景解析 | M2 / 统一层 | 同一套 SDF 盒体解析；M2 的 include 未建图问题依旧 |
| 运行协调/反馈/工作台/行为 | **基座** | 独有，统一层不碰 |
| 报表可追溯 | 统一层 | manifest + 输入/输出哈希；M2 只有文件输出 |

因此“最终版本”采用：**基座做运行与展示，`interop` 做 4.1/4.2 规划与对比**。
不建议把 M2 整体覆盖到基座，也不建议用统一层替换 `CoordinatorV2`。

## 7 边界与未做

- 统一层**只做四类中性任务**；T-ASL、攻击阵位、`fires`、毁伤/效果判定明确
  不在一层，解析阶段拒绝而不是降级。
- 计划没有执行证据：`result_status=PLAN_ONLY`、`evidence_source=NO_EXECUTION_EVIDENCE`。
- 任务段动作（巡逻绕环、侦察覆盖、封控拦截、坚守换班）仍由基座行为层接管；
  统一层只输出 TRANSIT/HOLD/STOP。
- 能耗/风险系数是演示值；跨后端只比硬指标，不比能耗/风险绝对值。
- 统一层是离线一次规划（秒级），不是 20 Hz 在线规划；未接 ROS/Gazebo。
- 本轮改动未提交 Git；文件清单见 `git status`（`interop/`、测试、两份 README、
  三份 outputs 对比目录）。
