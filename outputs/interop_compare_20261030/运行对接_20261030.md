# 融合版作为新主体：运行对接记录（2026-10-30 晚）

## 结论

`interop` 不再只是离线规划/对比工具，已经接到基座的运行链上，成为中性任务
场景的**默认规划引擎**：

```
4.1 消息 + 编成表（权威输入）
      ↓  interop.message / templates / scheduler / routing
统一计划（槽位、时刻、路径、风险/能耗）
      ↓  interop.runtime.InteropPlanner
基座 CoordinatorV2（下发、反馈、取消/确认/重试）
      ↓
mock_fleet 执行 → 工作台回放 / report.html / trajectory.html
```

**换的是规划引擎，不是运行语义**：命令身份与尝试、反馈核对、取消确认、
平台唯一指令源、工作台回放全部沿用基座。统一层只回答“谁、何时、走哪条路、
做哪个作业”。

## 1 新增的对接点

| 对接点 | 位置 | 行为 |
| --- | --- | --- |
| 可插拔规划器 | `coordinator_v2.CoordinatorV2(planner=...)` | 默认仍是 `planner_v2`；传入对象则每次滚动规划调用它，返回 job 级 `Plan` |
| 统一层运行适配 | `interop/runtime.py` | 快照平台位姿/存活/在途占用与剩余工作量 → 统一层规划 → 折回 job 级 `Assignment` |
| 基座入口 | `run_demo_v2.py --planner auto\|base\|interop` | `auto`（默认）中性场景用统一层，遇突击/效果判定自动回退基座 |
| 统一入口 | `interop.cli demo` | 4.1 输入直接跑完整运行链，同时输出 4.2 计划与运行报告 |
| 工作台 | 新建演示的“规划器”选择 | 场景 `interop_neutral` 固定用融合统一层；其它场景仍用基座 |
| 启动器 | `planning_middle_demo/启动融合版.cmd` | 一键跑中性样例并打开运行报告 |

运行视图：`to_v2_dict` 把 4.1 输入转成基座能吃的 v2 字段，但把原始
消息/编成表完整放在 `_meta.interop`，并标 `authoritative=false`。它是
**运行替身视图**，不是“无损旧场景转换”；`to-v2` 仍按既有规则拒绝有损转换。

## 2 关键语义对齐

| 问题 | 处理 |
| --- | --- |
| 统一层按“槽位时长”排程，基座按“成员 work_rate 累计”记进度 | 回写时令 `job.work = 槽位时长 × 成员 work_rate 之和`，使计划完工与实际进度同口径 |
| 基座没有“同作业多段串行槽位”的表达 | 运行快照把所有槽位对齐为同时开始，分组后的 start/end 才是一个真实作业区间 |
| 重规划不知道平台正忙 | 快照把在途指令的 `expected_end` 写成平台 `busy_until_s`，调度从该时刻起算 |
| 平台编号两套（U1 / rover_XX） | 运行时用 `robot_id` 映射到 `/rover_XX/cmd_vel` 身份 |
| 突击/效果判定场景 | 明确拒绝或回退基座，不降级、不猜语义 |

## 3 实测

### 3.1 统一入口（4.1 → 运行）

```powershell
cd planning_middle_demo
python -m interop.cli demo `
  --message interop/scenarios/mixed_inspection.message.json `
  --formation interop/scenarios/mixed_inspection.formation.json `
  --out ..\outputs\interop_demo\runtime_mixed --max-ticks 260
```

结果：

- 4.2 计划：4 个父任务 / 9 个槽位全部落实，makespan 210.0 s，0 冲突；
- 运行：`planner=interop`，4/4 完成，makespan **210 s**，与计划一致，
  27 次滚动规划，0 重试、0 超时；
- 作业实际区间：T1 17–137、T2 10–40、T3 60–210、T4 40–100；
- 产物：`..\outputs\interop_demo\runtime_mixed\`（plan.json、report.md、
  run/report.json、run/trace.jsonl、run/report.html、run/trajectory.html）。

### 3.2 工作台端到端（HTTP）

用工作台真实接口 `POST /api/runs` 提交：

```json
{"scenario": "interop_neutral", "planner": "interop", "motion": "teleport",
 "max_ticks": 260, "objective": "makespan", "avoid": false, "behavior": false}
```

结果：`workbench_20261030_174815_379279`，`state=complete`，
`planner=interop`，4/4 完成，makespan 210 s，产物含 `report.html` /
`trajectory.html` / `manifest.json`（manifest 记录 `planner` 与两个输入哈希）。

### 3.3 基座入口与回退

- `run_demo_v2.py --scenario <带 _meta.interop 的场景> --planner auto`：
  report 记录 `planner=interop`；
- `run_demo_v2.py --scenario scenarios/fleet_demo.json --planner auto`：
  因含 assault 作业回退，report 记录 `planner=base_v2`，运行正常。

### 3.4 不可行任务的运行表现

用 `capability_gap`（含“没有平台同时满足 RCN3+HLD2”和紧窗口）跑 160 步：

- `planner=interop`，2/4 完成；T2/T3 未分配；
- 运行报告 `need_report=['T2','T3']`，`rejected_reasons` 记录“融合层未凑齐兵力”；
- 没有静默丢弃、没有把不可行任务算成成功。

### 3.5 测试

`python -m unittest discover -s tests`：**168 项通过**。新增运行对接相关测试：

- 4.1 运行视图能通过基座 `check_scenario_v2`，且保留原始 bundle；
- 统一规划器在基座 `CoordinatorV2` 上端到端跑通（`planner=interop`）；
- 含 assault 的 v2 场景被明确拒绝；
- 工作台只接受 `interop_neutral + interop` 组合，其余组合报错。

## 4 边界（未变）

- 只做 T-RCN/T-SEC/T-PTL/T-HLD；**不含 T-ASL、攻击阵位、fires、毁伤/效果判定**。
  含 assault 的场景继续走基座 `planner_v2`，本层不接管。
- 计划仍是 `PLAN_ONLY / NO_EXECUTION_EVIDENCE`；运行报告来自 `mock_fleet`
  本地替身，不是 ROS/Gazebo 实测。
- 任务段动作（巡逻绕环、侦察覆盖、封控拦截、坚守换班）仍由基座行为层
  接管；本次 `interop_neutral` 演示是 `teleport` + 无到位行为，避免把
  “规划接通”误写成“动作验收”。
- `to-v2` 的有损性检查仍然生效，不因为“融合版是主体”就放宽。

## 6 2026-10-30 晚补充：话题改名与工作台修复

### 6.1 ROS 2 话题改名

移动话题从 `/rover_XX/cmd_vel` 改为容器命名空间 + 三位编号：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 移动话题 | `/rover_01/cmd_vel` | `/container_00/robot_001`（无 `/cmd_vel` 后缀） |
| 位姿话题 | `/model/rover_01/pose` | `/model/robot_001/pose` |
| 内部平台 ID | `rover_01` | 保持 `rover_01`（只作规划/反馈/工作台标识，不是 ROS 名） |

实现集中在一个地方：`planning_middle_demo/fleet.py` 的 `topic_of()` /
`pose_topic_of()`，`contracts_v2.delivery_block`、计划输出、`ros2_commands.txt`
都从这里取名。容器名/位姿前缀/可选后缀可用环境变量覆盖：
`FLEET_CONTAINER_NAME`、`FLEET_POSE_PREFIX`、`FLEET_CMD_SUFFIX`（例如桥接
仍要 `/cmd_vel` 时设成 `/cmd_vel`，不在代码里猜）；完全不一致时用
`FLEET_CMD_TOPIC_TEMPLATE`（占位符 `{robot}`/`{robot_no}`/`{no}`/`{container}`）。
仓库里的 `run_gazebo.sh` 目前仍把 ROS 侧桥成 `/robot_XXX/cmd_vel`；若实际
运行的是这份脚本，用模板 `/robot_{robot_no:03d}/cmd_vel` 即可对上，不必改
规划代码。

计划产物新增 `ros2_commands.txt`，每条是可直接粘贴的命令：

```text
# CMD-00027  at=0.000 s  duration=5.307 s  phase=TRANSIT
ros2 topic pub -r 20 /container_00/robot_041 geometry_msgs/msg/Twist "{linear: {x: 25.000, y: 0.000, z: 0.000}, angular: {x: 0.000, y: 0.000, z: 0.500}}"
```

注意：用户示例里的 `Z` 是大写笔误，ROS 2 的 Twist 字段必须小写 `z`；命令话题末尾
的 `/` 也按笔误处理（ROS 2 话题名不以 `/` 结尾）。若桥接确实要求后缀/尾斜杠，
应改桥接或显式设置 `FLEET_CMD_SUFFIX`，不要让每个输出文件各自拼字符串。

验证：

- 四组 4.2 计划全部输出 `/container_00/robot_XXX`，无 `/rover_` 残留；
- 运行报告的平台话题、反馈/回放、工作台运行均使用新命名
  （`workbench_20261030_190412_659441`，4/4、makespan 210 s、`planner=interop`）；
- `interop validate` 与测试通过。

### 6.2 工作台打不开的原因与修复

现场排查：8766 端口被 **13:45 启动的旧工作台进程**占用。旧进程的
`validate_config` 不认识 `planner` 参数，选择 `interop_neutral + 融合统一层`
新建演示会返回 400；浏览器里表现为“融合版工作台用不了/打不开”。

修复：

1. 已停止旧进程并重启新版本；catalog 增加 `version` 与
   `features.planner`，页面显示版本，旧服务会明确提示“请重启”；
2. `workbench_server.py` 端口被占用时：若占用者是**当前版本**工作台则复用；
   若是旧版本/其他程序，则自动在下一个端口（8766→8771）启动并打开新页面，
   不再静默打开旧服务；
3. `启动工作台.cmd` 增加 `py`/`python` 回退和失败提示。

当前 8766 已运行新版：`version=2026-10-30-interop-map-fix`，
`features={planner:true, interop_scenario:interop_neutral, plan_schema:0.3}`。
