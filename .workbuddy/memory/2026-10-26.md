## 10:25 详解 trace + 核实"五类任务有没有真实动作"

用户问两件事：① `t=10 T04[10,71]P00,P11` 这类行怎么读；② 五类任务在程序里有没有真实动作（比如巡逻）。

### 核实结论：**没有任何真实动作**

用脚本打印了巡逻平台 P10 每步的真实状态（seed 0，T00 巡逻，作业点 (47.7, 86.5)）：
- 初始 (31.0, 73.0) → **第 11 步瞬间变成 (47.7, 86.5)，之后再也不动**。位置是 `p.pos = t.pos` 一行瞬移。
- 进度每步 **+0.6**，正好等于 P10 的 `work_rate`（uav_a=0.6）。12 步到位 → 归零重来。
  所以"巡逻第二圈"**就是进度条清零**，不是走回起点。
- **t=31 位置被拽到 (26.1, 80.5)** —— 因为 T01 封控也从 31 开始用 P10，同一台平台挂在两个任务上，
  每个 active 任务都执行一次 `p.pos = t.pos`，位置每步在两点之间跳。**这是重叠非法计划的直接后果。**
- **电量掉到 0.0 仍然 `running`** —— 没有耗尽停机逻辑（与调研文档"飞机 VelocityControl 不会因有电池自动禁飞"一致）。

### 五类在程序里的差别只有三处
1. 参数（work / crew / window / 载荷 / 传感器）
2. 判据函数（`criteria.py`）
3. **动作上完全没有区别**

每类缺的真实动作：巡逻缺路线/航点/传感器；封控缺区域几何/探测模型/拦截事件；
侦察缺 sensor footprint 与覆盖几何；突击缺效果评估模块；坚守缺位置在位判定。
**连"移动"都没有** —— 真移动在 `bridge.GoalController`，但未接入。

### 重要澄清
- "巡逻 7 次访问"里的"访问"是 `evidence.py` 从 `progress` 按段推导的**统计口径**，不是平台真的去了又回。
- "侦察覆盖 20/20"是 `int(progress/work*20)`，不是相机真的扫过 20 个单元。
- "第二圈归零重跑"是 `demo_pipeline.py` 里的**演示补丁**，系统本身（`--no-sustain`）干完一圈就 `done`。

### 设计取舍（要记住的理由）
**没有下游仿真时，做假动作只会自欺**。所以当前刻意只做"账"不做"戏"：
executor 只推进度、扣电、回传，不模拟运动、观测、打击。
代价是：2.2(3) 消解率、2.3 能力边界这些指标，**在真实动作缺位时无法真正验证**。

### trace 行格式（供以后解释）
`t=步号 作业[起,止) 平台列表 ；并行作业 ...`，止为**排他**（71 表示第 70 步是最后一步）。
连续多行相同 = 这一拍无新事件、只是在走时间。trace 停在 t=80 是因为 T01 区间 [31,81) 结束。

### 关键事实（来自 bridge.py，早已预见）

### 踩坑（真实运动暴露的瞬移掩盖问题，最有价值）
1. **带高度作业的 travel 漏算爬升**：瞬移口径 ceil(水平距离/速度) 忽略爬升 30 米 ÷ max_linear 的耗时，PLANE 实际 16 步 vs 瞬移算 8 步。
2. **平台朝向 yaw 漏算转向**：真实运动"先转后走"，上一作业结束后的随机朝向要多花转向时间（同距离 yaw=0 16 步 vs yaw=2.36 21 步）。
3. **时间语义必须拆分出发/开工**：瞬移下 `start=开工时刻`（出发=开工），真实下必须 `start=出发时刻(now)`、`end=now+travel+dur`，否则 `_dispatch` 的 `a.start<=now` 恒 false 导致永不下发。
4. **deviation 基准要用"预计开工时刻"**（now+travel），不是下发时刻，否则在途阶段进度为 0 会疯狂误报（82 次 deviation → 收敛到 0）。
