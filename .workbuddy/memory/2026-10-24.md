### 下游接口事实（抄录，可直接复用）
- **50 台固定编成**：UGV 01–20(20)、TANK 21–30(10)、PLANE 31–40(10)、WING 41–50(10)。
- 控制话题 `/rover_XX/cmd_vel`，**每台一个**，非广播；消息 `geometry_msgs/msg/Twist`。
- 可用字段只有三个：`linear.x`(m/s 前进)、`angular.z`(rad/s 转向)、**`linear.z` 仅 31–50（升降）**；
  其余恒 0。Z 轴向上，`angular.z>0` 俯视逆时针，**不要套 UE 坐标符号**。
- 位姿反馈 `/model/rover_XX/pose`（`tf2_msgs/msg/TFMessage`，只读），frame 带私有延迟信息，
  不能当标准 /tf 用。图像尚未发布为 ROS 2 Image 话题。
- 发令约 20 Hz（0.05 s）；**无超时自动停车**，停止必须显式发全零；
  **同一机器人只安排一个持续发令源**。
- 环境：ROS 2 humble，`ROS_DOMAIN_ID=46`，`ROS_LOCALHOST_ONLY=1`。
- 边界：差速驱动（坦克只是履带外观）；飞机是关闭重力刚体 + VelocityControl 简化运动，
  无气动/失速/飞控/自动起降；**没有"到达目标点""执行航线""自动避障"的话题或 Action**。

### 三个关键结论
1. **下游没有"到达目标点"** → 我们下发任务级指令、下游只吃速度级，**中间缺一层，必须我们补**。
2. 说明第 4 节："速度按仿真时间生效、Seconds 按墙钟时间算，**RTF<1 时不能用 速度×秒数 推位移**"
   → **开环定时到不准，翻译层只能做闭环**（读位姿 → 每拍重算 Twist）。
3. **我们的速度参数与下游不是一个量级**：我们 ugv/uav_a speed 1.0/2.0（单位/步），
   下游实测 0.2/1.0 m/s。场景平均两点距 ≈52 单位 → 我们算 52/26 步，下游要 260/52 秒。
   若 1 步=1 秒，走完全场 260 步 > patrol 窗口 60 步，**作业根本走不到**。

### 两份新文档的关键约束
《五类作战任务_图文版》（甲方式稿）：
- 状态 **7 种**，含 **"结果待确认"**（我们只有 open/running/done/failed，缺两个）
- 判据必须写清**五件事**：对象 / 时间 / 门槛 / 证据 / 缺失处理（我们一个都没有）
- **全过程要求不能只检查最后一帧**（我们正是只看 progress）
- **完成条件（合不合格）与优化指标（哪种更好）分离**（我们现在混在 reward 里）
- **0 次事件不能写成 100%**；缺日志 ≠ 零事件
- 巡逻含首尾等待；封控"到位≠控制、发现≠阻止、无目标≠能处置"；
  侦察覆盖是**并集不是相加**、必查项独立于总量门槛；突击**预测概率≠已发生结果**；
  坚守**最后一帧和平均值不能代替全过程**、轮换要记接替时刻。

《四类平台参数指标与Gazebo实现详尽调研》核心结论（**最关键一句**）：
> "现有 50 路 cmd_vel **尚不能证明模型具备某一真实平台的最大速度、载荷、续航或飞行能力**。"
→ **我们能力闸门的速度/载荷/续航/传感器四项全部无真实来源**，这是"输入不存在"不是"精度不够"。
另：Twist **无 Header**（无时间戳/坐标系/目标点/载荷/续航）；飞机 VelocityControl **不会因有电池
自动禁飞**、耗电可能绕过触发路径；图像**未发布为 ROS 2 Image** → sensor 字段无来源。

## 19:35 补 L5 证据层 + 可运行演示，回答"实现程度多少、怎么跑"

用户要求：列出实现程度，并跑一次看 输入→规划→执行→输出，尤其五类怎么运行。

**新增 `planning/evidence.py`（L5）**：`Recorder`（含 state 派生状态）+ `observe_step()` +
`relay()` / `result()`。三条派生规则写在文件头（我方暂定）：
巡逻 把 work 切成 legs 段、每完成一段记一次有效访问；侦察 把待覆盖量离散成 cells 个单元；
封控/坚守 每步记 presence（这个不派生，是执行事实）。
**关键一处**：`observe_step` **不因 status=="done" 停止记录**——持续型要求维持到窗口结束，
若在 done 时停止记录就等于把"持续型被做成瞬时型"这个缺陷藏起来。照实记，让判据去判。

**新增 `planning/demo_pipeline.py`**：一条命令看全链路，五类各一个作业。
默认 `--steps 100 --H 45 --K 0`（K=0 = 只规划一次）。
跑出来 **5/5 success**；旧口径(progress>=work)只有 4/5。

**踩的三个坑（都是真 bug，不是格式问题）**：
1. `judge_hold` 把"累计 presence 条数"当成"当前在位台数" → 改成按 source 去重、按时刻取。
2. 巡逻的访问对象不区分圈次，同一段 L0 只记一次 → 改成记"刚完成的那一段"(prev)，不去重。
3. executor 活跃条件是 `start <= now < end`，想让 window[1] 那一步也在区间内，`end` 要给 **window[1]+1**。

**五个故意弄坏的场景全部能照出来**（这就是判据层的价值）：
`--no-sustain` → 巡逻/封控/坚守 fail（旧实现干完就放人）；
`--hold-drop-at 25` → 坚守"第 25 时刻在位 1 < 2"（轮换缺口）；
`--no-confirm` → 突击 pending_confirm；
`--K 5` → 滚动重规划把持续型打断 → fail（**重要发现：滚动时域会打断持续型任务**）；
`--event-at 20` → 事件闭合正常。

**另一个实测事实**：`--H 20` 时封控与突击**排不进去**（续航不足 + 超出视野），
H=45 才 5/5。与之前 H 扫描结论一致（H 是最灵敏的旋钮）。

**16 号补记（重要发现）**：`--sustain` 是**事后延长 `end`，不重新排程**，因此制造
**3 处同平台同时段重叠**（P00: T04[10,71]∩T03[39,44] 5步；P10: T00[11,61]∩T01[31,81] 30步；
P04: T01∩T03 5步）。**原始计划（不加补丁）重叠数为 0**，首尾相接：
T04[10,19] T00[11,31] T02[16,22] T01[31,39] T03[39,44]。
→ 结论：**"持续型维持到窗口结束"会改变可行性，必须进排程重解，不能事后打补丁**；
且**判据层管不了计划合法性**，两张检查必须都做。已在 `demo_pipeline.find_overlaps()` 里
加了这条检查并在输出中告警，避免被"5/5 success"误导。
