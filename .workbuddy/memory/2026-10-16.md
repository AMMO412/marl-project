### 已核实的 MARLlib 源码事实

- `core/` 下不是"一个算法一个模块"：IPPO 在 `IL/ppo.py`（IPPOTrainer），VDN/QMIX/IQL 共用 `VD/iql_vdn_qmix.py`（JointQTrainer）；`core/VD/vdn.py`、`core/IL/ippo.py` 都不存在，按算法名直接 import 必失败。
- VD 族配置的 `config["model"]` **只有 custom_model_config，没有 custom_model**（模型经 JointQPolicy 的 `default_model=JointQMLP/JointQRNN` 传入），强制 `config["model"]["custom_model"]` 必抛 KeyError。
- VD 族推理形态与 IL/CC 不同：`run_vd.py` 用 `with_agent_groups({"group_all_": env.agents}, ...)` 把全队合成一个"组智能体"，一次调用吃全队观测、吐全队动作；IL/CC 是逐个智能体调用。
- 调用链可用口径：原始分组观测（list of `{"obs":...}`）→ `Trainer.compute_single_action` 会先用训练期同一个预处理器压平成向量 → JointQPolicy `_unpack_obs` 走 flatten 分支还原，因此**必须传原始分组观测、且必须经 Trainer 调用**（直接调 policy 会绕过预处理器而炸）。返回值为长度=个体数的动作元组。
- 奖励口径一致：FCOOP 版 MPE 把团队奖励均分给每个个体（`reward/num_agents`），组包装器再求和 → CC/IL 与 VD 的 episode_reward_mean 同为团队回报，可直接比较。

## day1 第三轮：VD 评估修复（mappo/ippo 评估已成功，vdn/qmix 仍未通过 → 已定位并修复）

- 实测：EVAL_ONLY 重跑后，mappo / ippo 评估完整产出（episodes.csv / summary.json / trajectories.json），showcase.html 已生成；vdn / qmix 均失败在**构造 Trainer 时**，尚未进入推理。
- 新根因（本机源码核实）：MARLlib 只在 **训练进程内** 注册组环境名。`run_vd.py` 中 `env_reg_name = "grouped_" + env + "_" + map_name`，`register_env` 的工厂返回 `ENV[mpe](env_args).with_agent_groups({"group_all_": env.agents}, obs_space=Tuple([GymDict(space_obs)]*n), act_space=Tuple([space_act)]*n))`。评估进程直接拿 params.pkl 里的 `config["env"]`（值为 `grouped_mpe_simple_spread`）去建 Trainer，该名未注册 → RLlib 抛 `EnvError: The env string you provided ('grouped_mpe_simple_spread')`。
- 预读源码发现的另外两个必然触发点（未等到报错就修）：
  1. `JointQMLP.forward` 读 `hidden_state[0]`，而 `Policy.compute_actions_from_input_dict` 在无 `state_in_*` 时传 `state_batches=[]` → `_mac` 传空列表 → **IndexError**。必须把 `policy.get_initial_state()`（JointQPolicy 已覆盖，返回 `[s.expand([n_agents,-1])]`）作为 `state` 位置参数传入 `Trainer.compute_single_action`。
  2. `Trainer.compute_single_action` 的返回逻辑是 `if state or full_fetch: return action, state, extra else: return action`。联合 Q 的 state 恒非空，所以返回值是**三元组**而非裸动作；直接当动作用会拿到 (动作, 状态, extra)。
- 本轮改动（`evaluate_checkpoint.py`）：新增 `register_grouped_env()`（用 `marl.make_env` + `with_agent_groups` 复刻 run_vd 的注册，须在 `ray.init()` 之前调用）；新增 `query_actions()` 统一封装「传 state + 拆三元组」；`initial_state` 由 `policy.get_initial_state()` 取得，仅 joint-Q 使用；新增打印 `GROUPED_ENV:` / `INITIAL_STATE_SHAPES:` 便于从日志核对。
- `run_day1.sh`：新增 `SHOWCASE` 开关（默认 1），循环结束后自动用 compare_algos.py 重建 showcase.html。
- 第四轮实测反馈（EPISODES=5/30 重跑）：组环境注册与 initial_state 修复**已生效**（不再报 `EnvError: grouped_mpe_simple_spread`），VD 推进到 `JointQPolicy.__init__`，新报 `KeyError: 'reward_standardize'`。
- 第四轮新根因（已定位并修复）：`run_vd.py` 训练时**用的不是裸 `JointQTrainer`**，而是 `scripts/vdn_qmix_iql.py` 里 `JointQTrainer.with_updates(default_config=JointQ_Config)` 派生的类；`JointQ_Config` 额外带 `reward_standardize / optimizer / mixer / training_intensity / lr / buffer_size / train_batch_size / target_network_update_freq / learning_starts / exploration_config`。这些键**既不在 Ray 自带 qmix DEFAULT_CONFIG 里，也不会进 params.pkl**（params.pkl 只有 tune 传入的 model + run_config），所以裸 JointQTrainer 必炸。MAPPO 不炸是因为它需要的键全在 default_config 里。
- 参数取值来源：`_Algo.__call__(hyperparam_source=...)` 返回的 `algo.algo_parameters["algo_args"]`（读 `hyperparams/finetuned/<env>/<algo>.yaml`），再用 manifest 的 `algo_args` 覆盖（如 vdn 训练传了 batch_episode=8，yaml 默认 128）。新增 `joint_q_config_patch()` 复刻 `scripts/vdn_qmix_iql.py` 的公式；**只补 params.pkl 缺失的键**，已有的一律保留（params.pkl 里的值才是实际训练值）。新增日志 `JOINT_Q_CONFIG_ADDED:`。
- 无需跑机即可验证的新方法：**Ray tune 的 trial 目录下有 `params.json`**，是纯 JSON，Windows 侧可直接读，用来离线核对 params.pkl 内容，比反复跑机快得多。
- 用 params.json 核实到的三个事实：
  1. `params.json` 顶层只有 10 个键（env / model / multiagent / num_workers / seed / framework / evaluation_interval / num_gpus / num_gpus_per_worker / simple_optimizer），`reward_standardize / optimizer / mixer / training_intensity / lr / train_batch_size / buffer_size` **全部缺失** → 证实"只补缺失键"的补丁方向正确。
  2. 四个算法训练时的 `force_coop` 都是 **False**，但 `run_vd.py` 用 `from marllib.envs.global_reward_env import COOP_ENV_REGISTRY as ENV_REGISTRY` 把 COOP 注册表起别名，所以 **VD 训练始终跑在 FCOOP 环境上，与 force_coop 标志无关**（`run_cc.py` / `run_il.py` 则不导入注册表，用 build_env 按 force_coop 选）。已把 `register_grouped_env` 改为直接使用 `COOP_ENV_REGISTRY`。
  3. 奖励口径在各族之间确实可比：base MPE 每个体拿自己那份、FCOOP 每个体拿 team/3、组包装器再求和，**两种路径 sum 后都等于团队奖励**，IL/CC 与 VD 的 episode_reward_mean 同口径。
- 新增诊断打印：`ROLLOUT_ENV:`、`POLICY_CLASS:/OBS_SPACE:/ACT_SPACE:`、`JOINT_Q_CONFIG_ADDED:`，便于从日志核对而不必跑第二次。

## 重要更正：QMIX 并未持续恶化（此前的结论是错的）

- 回查 manifest + progress.csv 得出真实口径（10 次迭代滑动均值）：
  | 算法 | 训练总步数 | 100k 处 | 训练终值 |
  |---|---|---|---|
  | VDN | 500k | -94.9 | **-92.2** |
  | IPPO | 100k | -99.1 | -99.1 |
  | MAPPO | 100k | -103.1 | -103.1 |
  | QMIX | 500k | -197.8 | **-107.1** |
  | 随机 | — | — | -111.6（冻结评估均值） |
- **此前告诉用户"QMIX 远差于随机且持续恶化"是在 10 万步截断处的误判**。QMIX 在 100k 处谷底 -197.8，但跑到 500k 后恢复到 -107.1（仍最差，仅略低于随机基线 -111.6 一步之遥）。已在对话和 Obsidian 笔记中显式更正。
- 教训：四算法样本预算不等（CC/IL 10 万步、VD 50 万步），**任何跨族比较必须标步数**，不能以"500 迭代"为共同横轴截断对比。
- 另一个口径区分：上表是**训练期滑动均值**；随机基线的 -111.6 是**冻结独立评估**均值。二者不可直接相减。
