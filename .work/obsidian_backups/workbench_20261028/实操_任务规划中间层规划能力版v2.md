## 踩过的坑（比结论值钱）

1. **时间语义错位**（最大的坑）。旧版 `planner.py` 的 `start = now + travel` 是"开工时刻"，`executor.py` 用**瞬移**（`p.pos = t.pos` 开工即到达）刻意避开了"在途"。我一开始让 mock_fleet 逐步模拟在途，结果协同作业进度长期落后 planned_end，反复超时。**最终回退到瞬移语义，对齐原版**——逐步在途会让平台位置在滚动重规划中漂移，travel 反复被重算，作业永远做不完。

2. **偏差检测的基准漂移**。`_deviation` 若拿"当前计划的 a.start"算期望进度，滚动重规划会重置 a.start，期望进度反复清零，lag 永远累积不到阈值。修复：给 Job 加 `started_at/planned_end`（首次下发时固定），用固定基准。

3. **KEEP_COMMITMENT 必须保持原 start**。滚动重规划若把已承诺作业的 start 重置为 now，开工基准每滚一次往后挪一次，作业做不完（原版注释就警告过，我先改丢了这层保护又加回来）。

4. **mock_fleet 的 key 不一致**。`_platform_state` 用 `robot_no`（int）做 key，`_event` 用 `worker_id`（"rover_XX"）读，导致 pos/battery 永远读不到默认 (0,0)/0.0。统一用 worker_id(pid)。

## 2026-10-26：运动回放改造与距离修正

**已验证**：原 `run_20261026_214515_752916` 的 `trajectory.html` 已由静态折线改成离线播放器，支持播放/暂停、倍速、逐步、时间轴、事件跳转及单台追踪。报告首页增加回放入口，后续新运行自动生成。图上用单台颜色和类别形状区分平台，显示全部10台，含无位置反馈的闲置平台。

- **时间语义**：`real` 是本地逐步运动模拟，仅在相邻逐步反馈间做播放显示插值；`teleport` 按时间跳变，稀疏反馈保持最近位置，不补造连续运动。没有反馈的平台保留场景初始位，未知电量显示“—”。

**已核对的设计缺口**：`contracts_v2.py` 的 `JOB_SPECS` 通过工作量、窗口、人数、载荷、传感器与高度区分类型，`task_block` 也下传 `jtype`；但 `mock_fleet.py` 没有按 `jtype` 切换执行行为。`poll` 统一到目标、累计 `work_rate`、以 `progress >= work` 判完成。这解释了五类任务的轨迹看起来相似：原日志没有记录分类型执行行为，播放器不能补成已经发生的动作。

**解释口径**：任务差异不必表现为每一类都持续移动；定点作业可以静止。要证明任务语义已实现，需要对应的执行过程与可检验完成条件，而非仅换轨迹颜色或增加展示动画。当前日志6/6只能说明抽象工作量达标，不能作为五类任务行为验收。此结论不变更已有模块责任分工，本轮没有扩展任务执行或规划逻辑。
