## 0 三条硬约束（先记住，再动手）

| 约束 | 含义 | 违反的后果 |
| --- | --- | --- |
| **抽象效果语义（不做实弹级建模）** | 允许任务带 abstract effect（damage/suppress/seize/失控事件），由执行层 `Adjudicator` 回传；默认 `StubAdjudicator`、`verified=false`。**不允许**真实弹道、命中概率、毁伤/杀伤模型、武器性能参数，也不允许规划层预测成败。 | 越界会破坏"可复现、可追溯"的结论；把桩判定当战果会被评审推翻；真实毁伤/武器建模超出本项目范围 |
| **4.2 输出契约不变** | 新任务仍然只产出 `plan.json / assignments.csv / commands.csv / ros2_commands.txt / report.md`，字段不新增、不改名；`commands` 只表达 TRANSIT/HOLD/STOP 六分量速度 | 破坏 Gazebo/ROS 对接；历史回放与对比失效 |
| **不把本地替身当联调** | 报告与文档必须写清"本地行为状态机 + 4.1 输入回放"，未接真实平台/ROS/Gazebo | 结论越界，后续验收会被推翻 |

### 0.1 "抽象效果"具体能写到哪一步

项目里 `assessment.py` 已经给了现成边界，照它做即可：

- **可以**：`effect_kind = damage / suppress / seize` 这类抽象效果；`Adjudicator.adjudicate(task_ref, evidence)`
  回传 `items/overall/adjudicator/verified/note`；效果来自执行层证据（事件时间线、在位、占位、
  通信与传感器状态），默认桩判定并显式标 `verified=false`；
- **可以**：把"敌方进攻、阵位失守、控制权丧失、火力覆盖可用性"当作**输入事件或状态**建模
  （T-HLD 的"击退进攻""火力控制"都可以这样落地），不模拟弹道与命中；
- **不可以**：弹道/命中概率/毁伤半径/穿透等物理模型；武器选型与性能参数；为目标选择做
  "打击排序/毁伤最优化"；在规划期输出"预计摧毁/预计成功"；
- **表述纪律**：任何效果结论必须带"桩判定、未验证、需外部裁决"的标注，不得写成实战结论。

> 简言之：**从"完全不含效果"放宽到"只做抽象效果 + 桩判定"**，这条可以去掉；
> 但"不建真实武器/毁伤模型、不在规划层判成败"这条建议保留——它既是项目边界，也是
> 让结论站得住的前提。

另外两条协作纪律（来自 `AGENTS.md`）：

- 共享目录可能有别的 agent 在改：动手前 `git status`，不擅自回滚他人改动；提交只提交本轮授权的范围。
- 留痕放 `docs/` + `outputs/`，运行记录放程序内 `outputs/`，代表性记录才进 `.gitignore` 白名单。

## 1 融合版的整条链路

```
4.1 任务消息(schema 0.3) + 编成表
        │  interop/message.py  严格解析/校验（未知字段报错，不静默降级）
        ▼
统一 Scenario（平台、任务、约束、meta）
        │  interop/templates.py   分解：任务 → 子任务（槽位/角色）
        │  interop/gate.py        能力闸门（能力/载荷/窗口/续航/禁入区）
        │  interop/scheduler.py   协同分配（匈牙利）+ 风险 A* + 三目标评分 + 排程
        ▼
4.2 计划：plan.json / assignments.csv / commands.csv / report.md / ros2_commands.txt
        │  interop/runtime.py::to_v2_dict   计划 → 基座 v2 运行视图（_task_type/_behavior/crew）
        ▼
基座运行：CoordinatorV2（下发/反馈/重规划）+ MockFleet（替身）+ behaviors.py（任务段状态机）
        │  反馈轨迹 + 行为事件写入 trace.jsonl
        ▼
回放/呈现：trajectory_v2.py → replay.*（behaviors / containment / workers）
        ▼
工作台：workbench_server.py（HTTP/API）+ workbench/app.js + <task>.js（画布与面板）
```

**分工原则**（照做，不要越层）：

- 规划层只回答"谁、何时、走哪条路、去哪个作业点/阵位"；**不预测成败**。
- 执行层（behaviors）负责任务段动作与过程记账；判定与证据也在这一层产生。
- 回放层只从既有记录抽取数据，**前端不重算几何与指标**。
- 工作台只呈现，不改写结论。

## 2 区域封控到底做了什么（逐层清单）

### 2.1 4.1 输入样例

`planning_middle_demo/interop/scenarios/area_containment.{message,formation}.json`
（由 `interop/tools/build_scenarios.py` 生成，可重复）：

- 6 台平台：3 UGV + 2 TANK + 1 PLANE（编成表给能力、速度、起点=集结待机区）；
- T-SEC 任务：`defense_area` 140×90 m；`params.roles = {boundary:2, gate:2, intercept:1, air:1}`；
- 2 个通道口（方向/宽度）、传感器半径 40 m、内缩 14 m；
- 目标时间线：2 条未授权（1 条被拦阻、1 条警告后撤离）+ 1 条已授权（放行）；
- `assembly_point`、`air_unit`、`air_altitude_m` 等运行参数。

### 2.2 规划层

| 位置 | 做了什么 | 关键点 |
| --- | --- | --- |
| `containment_geom.py` | 边界弧长分段、段占位点、边界采样、覆盖比例、通道口、相遇点解算 | **规划层与执行层共用同一套几何**，否则"计划守东段、执行站西段"数据上分不清 |
| `interop/templates.py::_decompose_sec` | 按 `params.roles` 拆出边界段/门哨/机动/预备/空中槽位 | 目标仍只写 `{"point":[x,y]}`；角色写 `Subtask.role`（如 `boundary:1/2`、`gate:G-A`、`air:watch`） |
| `interop/scheduler.py` | 分配时把 `subtask.role` 落到 `Assignment.role` | 否则计划产物没有角色，执行层只能猜 |
| `interop/runtime.py::_sec_behavior_params` | 把 4.1 参数（区域/通道/目标时间线/巡视/空中）打包进 v2 job 的 `_behavior` | 只透传白名单字段；`roles` 单列 |
| `interop/runtime.py::nav_from_scenario` | 用编成表 `no_go` 约束构造 `NavMap` | interop 场景没有 `_meta.sdf`，**不能**用 `city_nav.build_nav`（会退到 simple_city 坐标） |
| `interop/runtime.py::InteropPlanner.__call__` | 把计划角色挂到协调器 job：`job._interop_roles` | 配合 `contracts_v2.task_block(roles=...)` 随指令下发给行为层 |

### 2.3 执行层

`behaviors.py::ContainmentBehavior`（`kind='blockade'`，仅当 `_behavior.area` 存在时启用；
旧的"环形占位"演示仍走 `BlockadeBehavior`）：

1. **占位建立**：边界段/门哨到位 → `control_established`，封控计时开始；
2. **在岗巡视**：占位组沿本段正弦扫掠（限速 2 m/s），门哨横向游走，机动组小圈待机；
3. **空中监视**：无人机爬升到 60 m，绕区盘旋，计入边界监视覆盖；
4. **发现/识别/警告/拦阻/越界/放行**：按 `control_level`（monitor/warn/block）与
   `engagement_authority`（none/self_defense/on_order）分支；
5. **结算**：`containment_result` 事件带 `verdict/reason/items/metrics/targets/timeline`。

配套改动（**这些是"能跑起来"的前提，不是可选项**）：

- `behavior_runtime.py`：每台平台独立 `PathFollower`（按平台速度定容差/前瞻）；
  行为可返回 `speed_scale` 限速；安全投影触发重规划时**强制重算**并允许原地转向（防活锁）。
- `city_nav.py`：前向安全投影距离上限 1.2 m（否则 8 m/s 平台在 1.5 m 通行间隙里永远判撞墙）。
- `mock_fleet.py`：`_behavior_job_dict` 透传 `_behavior` 与计划角色；
  `_behavior_structure` 输出封控结构（区域/分段/门哨/站位/空中高度）。
- `contracts_v2.py`：`TASK_TYPE_TO_JOB` 把 `_task_type` 派生为基座 `jtype`；
  `task_block` 增加 `roles` 字段。

### 2.4 回放层

`trajectory_v2.py::_containment_replay` 从 trace 里抽三块：

- `structure`：区域、分段边界折线、门哨、角色、传感器半径、空中高度；
- `result`：判定项、指标、逐目标轨迹、控制时间线；
- `events`：可逐条播放的控制过程事件（发现/警告/指派/拦阻/越界/放行/控制建立…）。

工作台消费 `replay.containment`，不重新推指标。

### 2.5 工作台

- 「演示总览」顶部两个**页签**：全局分配 / 区域封控，同一时间轴，切换互相同步；
- 全局分配：按"封控区 + 集结地"取景，实线边界 + 每台探测圈（实线），目标显示当前
  状态（按事件回推，而不是最终态）与拦阻连线；
- 区域封控页签：全程/封控区镜头、控制画面、6 项 KPI、目标闭合表、逐项判定、
  控制时间线、事件刻线；**规划路径默认关闭**（按钮可开），目标只留 12 s 尾迹。

## 4 4.1 / 4.2 契约（Gazebo 对接口径，不要动）

### 4.1 任务消息（schema 0.3）

```jsonc
{
  "schema_version": "0.3",
  "message_id": "...", "issued_at": "...", "source": "UPPER",
  "tasks": [{
    "task_id": "T1",
    "task_type": "T-SEC",            // T-RCN / T-SEC / T-PTL / T-HLD / T-ASL
    "priority": 1,
    "target": {"defense_area": [[x,y], ...]},   // 或 area/route/point/key_point/target_list
    "window": {"start_s": 0, "end_s": 600},
    "required_capabilities": {"HLD": 1},
    "min_units": 6, "max_units": 6,
    "params": { /* 任务专属，见 §5；未知字段不报错但必须登记 */ },
    "description": "..."
  }]
}
```

编成表 `formation.units[]`：`unit_id / robot_id / platform_class / position / speed_mps /
endurance_s / capabilities`；`constraints[]` 提供 `no_go`/`threat`；`meta.cell_size_m` 定义单位。

### 4.2 计划产物（每轮都必须齐全）

| 文件 | 内容 | 硬性要求 |
| --- | --- | --- |
| `plan.json` | `plan_id/schema_version/plan_version/generated_at/backend/objective/assignments/commands/conflicts/unassigned/metrics/explain`，`execution_scope=TRANSIT_AND_HOLD` | 字段不增删；`result_status=PLAN_ONLY`、`evidence_source=NO_EXECUTION_EVIDENCE` 只在纯规划时使用 |
| `assignments.csv` | `unit_id, robot_id, topic, platform_class, subtask_id, parent_task_id, task_type, role, target, start_s, end_s, window_start_s, window_end_s, depends_on, coordination, status, path_length_m, waypoint_count, risk, energy, path` | 列顺序不变；`role` 必须填（新任务的关键信息） |
| `commands.csv` | `command_id, attempt, action, robot_id, topic, unit_id, subtask_id, phase, at_s, duration_s, linear_x/y/z, angular_x/y/z` | `action ∈ {start,stop}`，`phase ∈ {TRANSIT,HOLD,STOP}`；STOP 必须全零 |
| `ros2_commands.txt` | `ros2 topic pub -r 20 /container_00/robot_XXX geometry_msgs/msg/Twist "{linear:{...},angular:{...}}"` | 话题规则 `fleet.topic_of`，20 Hz，小写六分量 |
| `report.md` | 计划摘要、角色、冲突、未分配、边界说明 | 必须写明"只有计划，无执行证据" |

**关键边界**：任务段动作（阵位内坚守、轮换、增援、拦截）**不进 commands**；commands 只到
`HOLD`（原地保持）。执行段行为写进本地回放与报告，不伪装成 ROS 指令。

## 6 踩坑清单（都是真踩过的）

> 用法：新任务遇到"动不了 / 不动 / 画错 / 看不见"时，先按这张表排查。

### 规划 ↔ 执行

1. **计划里有角色，执行层拿不到**
   现象：计划 `role=boundary:1/2`，行为层全按"未分工"跑。
   根因：`Assignment` 没带 `role`；或 `task_block` 没把角色传给指令。
   修法：scheduler 落 `role`；`InteropPlanner` 挂 `_interop_roles`；`task_block` 带 `roles`；
   `mock_fleet._behavior_job_dict` 合并进 `_behavior.roles`。

2. **行为层跑不起来 / 走向错误坐标**
   现象：`build_nav` 报找不到地图，或平台朝错误方向。
   根因：interop 场景没有 `_meta.sdf`，`city_nav.build_nav` 退回 simple_city 世界坐标。
   修法：`interop.runtime.nav_from_scenario(scenario)`，用 4.1 的 `no_go` 约束 + 作业范围构造 `NavMap`；
   在 `run_demo_v2.simulate(nav=...)` 注入口。

3. **空中平台被地面席位抢走 / 抢地面席位**
   现象：规划把无人机分到"边界段"，或地面车占了空中席位。
   根因：能力闸门只看 `required_capabilities`，不看"有没有高度层"。
   修法：该席位用 `pinned_unit`（4.1 的 `air_unit`）或专用能力编码；文档写清。

4. **兵力上限裁剪顺序乱**
   现象：6 台配置被 4 台上限裁成"没有机动组"。
   修法：固定裁剪顺序（预备队 → 空中 → 边界段 → 门哨），机动组最后裁；写进测试。

### 运动 / 行为层

5. **高速平台被压成 0.8 m/s**
   现象：编成表 8 m/s，实际只走 0.8 m/s。
   根因：`BehaviorRunner` 所有平台共用一个 `PathFollower(max_linear=0.8)`。
   修法：每台一个 follower，`max_linear=plate.speed`；容差/前瞻按 `speed*dt` 放大。

6. **平台原地打转 / 原地不动**
   现象：仿真跑完仍在起步点附近抖动。
   根因：高速下一拍跨过航点，前瞻点落到身后；安全投影判撞墙后 `continue`，既不转也不走；重规划又被"目标没变"挡住 → 活锁。
   修法：航点容差/前瞻随速度放大；投影距离封顶 1.2 m；重规划强制重算 + 1 s 冷却；重规划那拍允许原地转向。

7. **巡视被记成"脱岗"**
   根因：用"离指定点 ≤ ε"判在位，而平台在段内移动。
   修法：按职责范围判在位（边界段看弧长+带内距离，门哨看通道口半径）。

8. **控制中断每 5 秒刷一条**
   修法：一次离位只记一条 `control_interrupted`，回岗记 `control_restored`；机动组前出不算离岗。

9. **阶段名一闪而过**
   修法：先判"是否已处置完"再切阶段；把复位判断放在推进目标之前。

10. **拦截点落在花坛/墙里**
    修法：前出点 `nav.nearest_free` 吸附；报告里记吸附距离。

### 显示 / 回放

11. **目标状态时间错位**
    现象：T+55 s 就显示"已拦阻"。
    根因：直接用结果的最终 `state` 画。
    修法：按事件时间线回推当前状态（前端同一套 `targetStateAt`）。

12. **一屏虚线/长线看不清**
    修法：探测圈改细实线；规划路径默认关闭（按钮开）；目标只留 10–12 s 尾迹；去掉起点→目标长线；
    标注做矩形避让（放不下就不画，不叠字）。

13. **两个页签各有一个时钟**
    修法：切换时 `syncTime` 双向同步，避免"切过去又是 T+0"。

### 工程 / 环境

14. **"新建演示无效参数"**
    根因：浏览器连着旧的 `workbench_server` 进程（旧代码不认新场景）。
    修法：`features` 增加能力标志，前端检测后禁用场景并提示重启；重启 `启动工作台.cmd`。

15. **合并后出现重复键/重复块**
    根因：双方同时改 `workbench_server.py` 等文件，合并保留了两份。
    修法：合并后跑测试 + 逐文件 grep 关键常量；发现重复键立即清理。

16. **测试报 `PermissionError: chmod` / 中文乱码**
    根因：Windows 沙箱下 temp 目录清理 chmod 被拒；控制台是 GBK。
    修法：测试前把 `TEMP/TMP` 指到可写目录；脚本输出用 UTF-8 或直接读文件校验，不靠控制台。

17. **前端脚本引用 `window.state` 为空**
    根因：`app.js` 用 `const state = {...}`，是全局词法绑定，不在 `window` 上。
    修法：其他脚本用 `typeof state !== 'undefined' ? state : null` 访问。

## 9 要点坚守（T-HLD）任务书

> 依据：`资料/需求与任务/无人集群编队五类任务定义_1028.docx` §2.5（以及 §1.4/1.5 的判定与结算口径）。

### 9.1 需求摘要（提炼）

- **定义**：保持对指定要点/防御区域的控制；按威胁方向配置阵位；持续观察与（非）火力控制；
  阻止敌方夺取或恢复控制；触发条件下增援、轮换或撤离。
- **成功标准**：保持控制（要点未被敌方控制）、观察中断不超阈值、击退进攻、增援及时、
  结束/撤离合规。**平台损毁不是失败必要条件**，以控制权丧失/被迫撤离为主判据，损失计代价。
- **判据前提**：用"有效在位数量"时要说清位置范围/资格；用"观察覆盖下限"时要说清状态定义；
  数量与状态可同用但不得互相替代；轮换记录实际进入/离开/接替时刻，**计划轮换不算接替**；
  空窗与恢复分别留痕，按允许中断规则结算。
- **作用对象**：要点、防御区域、设施/基地、关键地形；给威胁方向、阵位、纵深；空中要点给高度层。
- **兵力**：阵位组、预备队、支援组、中继；最少平台数由威胁方向、阵位容量、支援距离确定。
- **决策要素**：阵位/扇区/威胁方向到平台分配；队形（环形/扇形/纵深/要点式）；相互支援、
  交叉火力、增援、交接、中继；进入阵位/换位/增援/撤离路线；通信与断链预案；交战规则；
  时序（占位→观察→交战→增援→轮换→撤离）。
- **边界**：不含主动突击/夺占、区域进出管制与拦截、以巡逻发现为主的任务、战略防御、
  非军事安保、无授权阵内反击/追击。
- **典型场景**：3 号高地 + 500 m 半径、2 个威胁方向、3 个预设阵位；2 架无人机观察、
  1 架预备；坚守 30 min；敌我比 1.5 或阵位失守请求增援；控制权丧失或被迫撤离转重规划。
- **可建模接口**：输入（要点/区域、威胁方向、预设阵位、坚守时长、增援触发、撤离位置、
  判据与资格、中断规则、结束/移交条件）；决策变量（阵位分配、预备队、观察扇区、
  增援路线、轮换、撤离时机）；约束（阵位容量、支援距离、续航、通信、交战规则）；
  指标（控制保持率、控制中断时间、增援到达时间、敌方突破次数、我方损失）。

### 9.2 本层做 / 不做

| 做 | 不做 |
| --- | --- |
| 阵位分配、预备队、轮换与接替、增援路线、撤离时序 | 真实弹道、命中概率、毁伤/杀伤模型、武器性能参数 |
| 在位/观察/空窗/增援/接替的过程记账与判定 | 规划期预测"能不能守住/打掉"、概率型成败 |
| **阵内反击、火力控制可用性、敌方进攻/突破**：作为 abstract effect 与输入事件，由执行层
  `Adjudicator` 桩判定（`verified=false`） | 为目标选择做打击排序/毁伤最优化 |
| 4.2 计划产物 + 本地行为回放 | 真实 ROS/Gazebo 联调结论 |

> 说明：1028 的"火力控制"是控制形态之一。本层把它建模成**状态/能力**（例如"该阵位火力覆盖
> 可用 / 被压制"）与**事件**（`suppressed`、`counter_attack`），不模拟开火过程与杀伤效果。

### 9.4 分解与角色（`_decompose_hld`）

- `post`：每个阵位 1 个槽位（目标=阵位点），角色 `post:P1`…；带 `facing_deg`。
- `reserve`：预备队待机点（默认要点后方/中心），角色 `reserve:standby`。
- `support` / `relay`：可选，目标分别为支援位与中继位。
- 兵力上限裁剪顺序：`support → relay → reserve → post`（**阵位最后裁**，否则没人守）。
- 复用 `containment_geom` 的方位/点计算（威胁方向 → 阵位朝向）；不要另写一套几何。

### 9.5 执行语义（`KeepBehavior`，`kind='hold'`）

建议与 T-SEC 对齐的时序：

1. **机动进场**：从集结地按 4.2 路径进入阵位/待机点；记录到达时刻。
2. **占位**：`post` 到点 → `on_post`；达到 `min_on_post` → `control_established`。
3. **观察**：按阵位朝向与传感器半径记录覆盖；`observation_gap > observation_gap_max_s`
   → `observation_gap` 事件（允许短中断时按阈值结算）。
4. **接替/轮换**：到 `relief.interval_s` 由预备队（或另一阵位组）前出；**接替者到位才撤**
   （`swap_requires_arrival`），记录 `handover_start/handover_complete`；未到位不得撤。
5. **增援**：触发条件（阵位失守/敌我比）= 输入事件 → 记录 `reinforce_triggered`，
   按路线前出，统计 `reinforce_arrival_s`；超时记 `reinforce_timeout`。
6. **阵内反击 / 火力控制（抽象效果，可选）**：仅当 `counter_attack.authorized=true` 且目标
   在阵位/射程范围内 → 生成 `counter_attack` 事件，交 `assessment.Adjudicator`（默认桩）出
   `achieved/failed/pending`，**写 `verified=false`**；压制状态记 `suppressed/restored`，
   只影响观察与在位判定，不生成任何毁伤数值。
7. **撤离/结束**：授权解除或被迫撤离 → `withdraw_started/withdrawn`；控制权丧失记 `control_lost`。
8. **结算**：`hold_result`（verdict/items/metrics/timeline/positions/effects）。

**控制权判定口径（必须显式写清）**：本层用"有效在位数量 + 阵位状态"代表控制权，
并声明这只是模型近似（1028 §2.5.2 明确覆盖状态不等于现实控制权）。

### 9.6 指标与判定

| 指标 | 计算 | 备注 |
| --- | --- | --- |
| 控制保持率 | 控制在位时间 / 坚守时段 | 主判据 |
| 控制中断时间 | 在位数量低于 `min_on_post` 的累计秒数 | 与允许中断对比 |
| 最长观察中断 | 阵位覆盖为空的最长连续秒数 | 主/辅判据按配置 |
| 增援到达时间 | 触发 → 增援到位 | 超时记失败项 |
| 敌方突破次数 | 敌方进入要点/阵位的事件数 | 本层用输入事件驱动 |
| 击退/反击效果 | 桩判定 `achieved/failed/pending` | **`verified=false`**，仅作过程证据，不作战果 |
| 我方损失 | 失联/损毁平台数 | **代价指标，不作失败必要条件** |
| 接替合规 | 每次轮换"到位才撤" | 计划轮换不算接替 |

判定：必需项全满足 → `succeeded`；控制权丧失/被迫撤离 → `failed`；结果需外部证据而未齐
→ `pending`（写清缺失项与确认时限）。**任何效果类条目都必须带"桩判定、未验证"标注**，
并且不得把 `pending` 解释成成功。

- [ ] 单测 ≥15 项，全量测试通过（当前基线 198）；
- [ ] `docs/` 与 `outputs/` 留痕，代表性运行入白名单。

### 9.10 建议实施顺序与风险

1. 最小可运行：单要点 + 2 阵位 + 1 预备 + 1 次轮换（先不接增援/反击）；
2. 加增援触发与到达时间统计；
3. 加观察覆盖与允许中断；
4. 再加多威胁方向、撤离、空中要点（高度层）；
5. 最后接抽象效果（反击/压制/敌方进攻判定，桩判定 `verified=false`）。

主要风险：**阵位数量与兵力上限**容易配成"没人守"；**轮换时"到位才撤"**如果漏掉，
会把空窗算成 0；**控制权口径**必须显式声明是模型近似，不能写成"已确认真实控制"；
**效果类条目**一旦忘记标 `verified=false`，就会被当成实弹战果。
