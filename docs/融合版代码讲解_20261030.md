# 融合版代码讲解（interop + 基座运行链）

更新日期：2026-10-30。本文按当前源码、`interop/scenarios/mixed_inspection.*` 和 `planning_middle_demo/outputs/workbench_20261030_210424_645030/` 核对重写。分析对象是当前主程序：`planning_middle_demo/interop/` 规划层 + 同目录基座运行层。

一句话：**输入用 1028 4.1、规划用 interop、运行与回放用基座 CoordinatorV2/工作台。**  
融合版覆盖五类任务（T-RCN / T-SEC / T-PTL / T-HLD / T-ASL）。T-ASL 只规划侦察/突击/评估席位与机动，打击动作与毁伤/压制/夺占判定仍由基座行为层与评估接口执行，融合层不判成败。`asl_city` 仍可在工作台作为历史场景查看/运行，它走基座原规划器与行为链；融合版的 T-ASL 样例是 `interop_asl`（`asl_junction.*`）。

## 2 项目范围与输入来源

### 2.1 范围

- **规划层**：`interop/`。负责 4.1 解析、任务分解、能力闸门、协同分配、A* 路由、三目标评分、排程、校验、4.2 导出。
- **运行层**：`coordinator_v2.py`、`mock_fleet.py`、`behaviors.py`、`city_nav.py`。负责命令下发、反馈核对、取消/确认/重试、逐步运动、回放。
- **展示层**：`workbench/` 与 `workbench_server.py`。
- **不并入**：M2 的 T-ASL/攻击阵位/`fires`/毁伤评估；基座的历史突击/效果链保持原样。

### 2.2 4.1 任务消息

必填：`schema_version`、`message_id`、`issued_at`、`source`、非空 `tasks`。

| 字段 | 约束 |
|---|---|
| `schema_version` | 必须是 `"0.3"`；其它版本报错 |
| `message_id` | 非空字符串 |
| `issued_at` | 带时间的 ISO 8601；只作追溯，不参与相对时刻换算 |
| `source` | 上级/调整/自主，或 UPPER/ADJUST/AUTONOMOUS |
| `tasks[]` | 非空数组；`task_id` 唯一；`depends_on` 或 `prerequisites` 不能同时给 |

单个任务字段：

| 字段 | 说明 |
|---|---|
| `task_id` / `task_type` | 任务编号 / T-RCN、T-SEC、T-PTL、T-HLD |
| `priority` | 1–5，越小越优先 |
| `target` | 恰好一种：`area/sector/patrol_area/defense_area/route/point/key_point/target_list` |
| `window` | `{start_s, end_s}`，秒；`end_s > start_s` |
| `required_capabilities` | 能力编码 → 等级（0–3），每台平台逐项达标 |
| `min_units` / `max_units` | 最少/最多兵力；`max_units >= min_units` |
| `params` | 任务模板参数，如 `duration_s`、`coordination`、`defense_positions` |
| `depends_on` | 前置父任务编号；不能成环、不能引用不存在任务 |
| `allow_split` | 是否允许按区域/路线拆分槽位 |

### 2.3 编成表

`formation.units[]` 沿用 M2 字段，并补基座画像：

| 字段 | 含义 |
|---|---|
| `unit_id` / `robot_id` | 规划编号（U1）/ 机器人编号（1–50） |
| `platform_class` | UGV 1–20、TANK 21–30、PLANE 31–40、WING 41–50 |
| `position` | `[x,y]` 或 `{x,y}`，场景单位 |
| `speed_mps` / `endurance_s` / `vertical_speed_mps` | 速度、累计续航、垂向速度 |
| `capabilities` | 能力等级，4.1 能力闸门用 |
| `payload/sensor/battery/work_rate/move_cost/work_cost` | 基座画像，运行适配/对比用 |
| `status` | READY/BUSY/DAMAGED/LOST/OFFLINE，只有 READY 参与当前候选 |

`meta`：`cell_size_m`（1 场景单位 = 多少米，默认 1）、`grid_cell_m`、`grid_margin_m`、`plan_id`。  
`constraints`：`no_go`（多边形、`applies_to=ground/all`、`height_m`）与 `threat`（`intensity`、`applies_to`）。

## 4 任务定义与分解

### 4.1 四类模板

| 类型 | 默认时长 | 默认拆分 | 关键参数 |
|---|---:|---|---|
| T-RCN | `duration_s=120` | 区域竖条 / 路线分段 / `target_list` 逐点 | `duration_s`、`coordination` |
| T-SEC | `hold_duration_s=600` | 入口点，或区域周界采样 | `entry_points`、`coordination` |
| T-PTL | `duration_s=300` | 路线分段 / 巡逻区域竖条 / 单点 | `handover_points`、`coordination` |
| T-HLD | `hold_duration_s=600` | `defense_positions`，否则 key_point/区域质心 | `defense_positions`、`coordination` |

拆分数量 `_units_for_split()`：

```python
n = READY 且能力达标的平台数
if not allow_split: n = 1
n = max(1, min(n, 4))
if max_units is not None: n = min(n, max_units)
```

这修正了 M2 的问题：M2 的区域/路线拆分不读 `max_units`，会拆出超过兵力上限的槽位。

### 4.2 本样例的分解结果

| 父任务 | 类型 | 槽位 | 目标 |
|---|---|---|---|
| T1 | T-SEC | T1-S1、T1-S2 | 两个入口点 (100,-60)、(125,-60) |
| T2 | T-RCN | T2-S1、T2-S2、T2-S3 | 3 个检查点 |
| T3 | T-HLD | T3-S1、T3-S2 | (56,60)、(64,60) |
| T4 | T-PTL | T4-S1、T4-S2 | 环形路线切成两段 |

协同：T1、T3 带 `simultaneous_arrival`；T2、T4 不强制同时开始。

### 4.3 `slots` 参数

`params.slots` 只给**运行适配器**用：基座 v2 的 `crew=N` 是“N 台平台合作同一作业”，没有“同作业多段串行槽位”的表达。工作台从 v2 导出任务时，用 `slots=crew` 把单点作业扩成 N 个同点槽位，并强制 `simultaneous_arrival`，分组后的 `start/end` 才对应一个真实作业区间。4.1 原生输入不带这个参数。

## 6 能力闸门与分配

### 6.1 能力闸门

`gate_platform()` 依次检查：

1. `status == READY`；
2. `required_capabilities` 每项达标；
3. 任务时长不超过窗口长度；
4. 任务时长不超过平台续航；
5. 目标点不在 `no_go` 内。

拒绝会带原因码：`STATUS`、`NO_CAPABILITY`、`WINDOW`、`ENDURANCE`、`NO_GO`、`NO_ROUTE`、`COORDINATION`、`DEPENDENCY`。父任务目标在禁入区时整组拒绝。

### 6.2 协同组

对带 `simultaneous_arrival` 的父任务：

1. 对“槽位 × 平台”构造代价矩阵；
2. `hungarian()` 求一对一最优；
3. 选中平台在组内全部槽位处理完前**预留**，别的任务不能抢；
4. 统一开始时刻：`group_start = max(每个槽位 max(free+travel, dep_ready, window_start))`；
5. 每个槽位用 `group_start` 覆盖开始时刻，实现“同时开始/到达”。

匈牙利只保证当前代价矩阵最优；阵位/目标是预先分解的，不把返程和后续任务联合优化。

### 6.3 代价模型

`CostModel.candidate_cost()`：

```text
cost = w_t * end_s/time_ref
     + w_r * risk/RISK_REF
     + w_e * energy/ENERGY_REF
     + 1e-3 * time_norm
     + 1e-9 * energy_norm
```

| 目标 | 权重（time, risk, energy） |
|---|---|
| timeliness | 1, 0, 0 |
| energy | 0, 0, 1 |
| risk | 0, 1, 0 |
| balanced | 0.5, 0.3, 0.2 |

能耗：`路径米 × e_m + 任务秒 × e_s`，按平台类给系数；风险：威胁区按采样段累计“强度 × 进入时长 × 信号特征 × (1-防护)”。系数是演示值，真实数据到位只改 `cost.py`。

### 6.4 路径

`Router.route()`：

- 地面平台：栅格 A*（8 邻域、octile 启发式、禁止斜穿角），可用 8 邻域比 M2 的 4 邻域路径更短；
- 空中平台：直线，不做地面绕行；
- `risk_weight > 0` 时威胁格边代价加权，路径主动绕开威胁；
- `risk_weight == 0` 时做视线捷径平滑；
- 栅格按几何/分辨率缓存（`_GRID_CACHE`），同一场景滚动规划不重复建图。

默认 `grid_cell_m=2`、`grid_margin_m=1.5`（样例），`cell_size_m=1`。

## 7 排程与运行对接

### 7.1 单槽位评估

```python
route = router.route(state.position, target_start, is_air)
motion = simulate_path(route.path, platform, state.heading)
travel_s = motion.duration_s
start_s = max(state.free_s + travel_s, dep_ready, window_start)
end_s = start_s + duration
if end_s > window_end: reject WINDOW
if used_s + travel_s + duration > endurance: reject ENDURANCE
risk = CostModel.path_risk(...)
energy = CostModel.energy(platform, route.length_m, duration)
cost = candidate_cost(end_s, risk, energy)
```

地面平台先原地转向再直行，转向耗时计入 `travel_s`；空中平台按最小转弯半径边前进边转向。

### 7.2 `InteropPlanner` 快照

每次滚动规划，`_snapshot(coord)`：

- 平台：用协调器当前 `pos/yaw/alive`；把 4.1 编成表的速度/续航/work_rate 同步给协调器；
- 在途占用：`platform_cmd` 对应的 `expected_end_sim_s` 写入 `busy_until_s`，新任务从该时刻起算；
- 任务：只保留 `status == "pending"` 的作业；依赖未完成的跳过，等下一次滚动；
- 剩余工作量：`scale = (interop_total - progress) / interop_total`，时长按剩余比例缩短；
- 协同：运行快照给所有槽位补 `simultaneous_arrival`，因为基座没有“同作业串行多段”的表达。

### 7.3 折回基座

每个父任务的分组：

```python
pids = 去重后的基座 pid（rover_XX）
start_task = max(now, min(槽位 start))
duration   = max(槽位 end) - min(槽位 start)
travel     = max(槽位 travel)
if motion == "real":
    start_task = max(start_task, now + travel)
    start = start_task - travel      # 基座 real 语义：start 是出发时刻
else:
    start = start_task               # teleport：start 是开工时刻
job.work = 时长 × 成员 work_rate 之和
```

`work = 时长 × work_rate 之和` 是运行正确性的关键：基座 `mock_fleet` 按“每台成员每步贡献 work_rate”累计进度；如果沿用 M2 的“槽位时长”，会出现“计划 150 s、实际 75 s 完成”或偏差检测反复触发。

协调器随后照常 `_dispatch()`：到 `start` 才发令、平台忙则等下一轮、按 `job.crew` 检查人数、超时只请求取消、失败可重试。

### 7.4 与真实运动的关系

工作台 `motion=real` 时，基座 `mock_fleet` 用 `GoalController` 做“先转后走”的闭环替身，**不是**按 interop 的 A* 航点逐点跟随。因此：

- 4.2 `plan.json` 里的 `path` 是规划路径，可在计划报告/几何审计里核对；
- 工作台轨迹是反馈位姿重建，可能与规划路径不完全重合；
- 这是本地替身的边界，不表示真实导航控制器已验证。

## 8 执行层与 ROS 2 话题

### 8.1 速度段

`build_commands()`：

- `TRANSIT`：按分配路径生成；地面先转后走，空中边转边走；
- `HOLD`：到达后全零 Twist，覆盖任务时段，按 120 s 切片；
- `STOP`：每台机器人最后一次作业结束后 1 s 全零；
- 同一采样合并（`coalesce`），单条不超过 120 s；
- 输出按 `(robot_id, at_s, phase)` 排序，再赋 `command_id`。

本样例机器人 42：

| CMD-00034 | TRANSIT | 0.000 | 3.647 | 25.0 | 0 | 0.5 | T2-S3 |
| CMD-00035 | TRANSIT | 3.647 | 2.802 | 25.0 | 0 | 0 | T2-S3 |
| CMD-00036 | HOLD | 6.448 | 30.000 | 0 | 0 | 0 | T2-S3 |
| CMD-00037 | TRANSIT | 36.448 | 3.647 | 25.0 | 0 | -0.5 | T4-S1 |
| CMD-00038 | TRANSIT | 40.095 | 2.522 | 25.0 | 0 | 0 | T4-S1 |
| CMD-00039 | HOLD | 42.617 | 60.000 | 0 | 0 | 0 | T4-S1 |

### 8.2 话题

2026-10-30 起：

| 用途 | 话题 |
|---|---|
| 移动 | `/container_00/robot_XXX`（三位编号，无 `/cmd_vel` 后缀） |
| 位姿 | `/model/robot_XXX/pose` |
| 内部 ID | `rover_XX`（不是 ROS 名） |

实现集中在 `fleet.py`：

- `topic_of()`：`/{FLEET_CONTAINER_NAME}/robot_XXX{CMD_SUFFIX}`；
- `pose_topic_of()`：`/model/robot_XXX/pose`；
- 覆盖：`FLEET_CONTAINER_NAME`、`FLEET_CMD_SUFFIX`、`FLEET_CMD_TOPIC_TEMPLATE`、`FLEET_POSE_PREFIX`、`FLEET_POSE_TOPIC_TEMPLATE`。

`ros2_commands.txt` 每条可直接粘贴：

```text

ros2 topic pub -r 20 /container_00/robot_041 geometry_msgs/msg/Twist "{linear: {x: 25.000, y: 0.000, z: 0.000}, angular: {x: 0.000, y: 0.000, z: 0.500}}"
```

注意：Twist 字段小写 `z`；话题名不以 `/` 结尾；`-r 20` 只是发布频率，持续时间由调用方按 `at_s/duration_s` 管理；文件只给命令，不自动发布。

## 10 工作台

### 10.1 当前界面约定

- 新演示场景下拉只有两个：**融合版中性任务**（默认）与 `asl_city` 历史入口；
- 融合样例固定 `interop` 规划器 + 逐步运动，界面不再让用户选规划器/运动模式；
- 突击效果类型只在历史 `asl_city` 显示；融合中性场景隐藏；
- 首页默认运行是最新一次融合运行；历史突击/行为记录仍在下拉；
- 根目录 `启动工作台.cmd` 直接打开 `/?new=interop`，自动弹出融合样例的新建表单。

### 10.2 服务端

`validate_config()`：

- `scenario` 只接受已知键；
- `planner=interop` 只允许 `interop_neutral`；
- `interop_neutral` 必须用 `interop`；
- 融合场景 `avoid` 强制 false，`behavior` 自动降级；
- 默认仿真步数：`asl_city=620`、`interop_neutral=260`。

`run_worker()`：

1. 读 request.json；
2. `interop_neutral`：读 4.1 消息+编成表 → `InteropPlanner`；
3. `simulate()` 跑基座协调/反馈；
4. 另跑一次 `interop.Planner`，把 4.2 计划包写入运行目录；
5. 写 report/trace/summary/report.html/trajectory.html；
6. manifest 记录输入哈希、`planner`、`plan_files`。

`catalog()`：版本、features、默认运行、运行列表。默认运行优先最新 `planner=interop`，其次 `asl_city` 行为记录。

### 10.3 端口与版本

- 端口被当前版本工作台占用 → 复用并打开；
- 旧版本/其他程序占用 → 自动换下一个端口（8766→8771）；
- catalog 带 `version` 与 `features.planner`；页面显示版本，旧服务提示重启。

## 11 字段消费者与实现边界

| 字段/机制 | 当前处理 |
|---|---|
| `required_capabilities` | 能力闸门硬过滤；基座 v2 契约没有该字段，故只在 interop 侧生效 |
| `window` | 排程硬约束；基座历史排程只检查截止，不检查窗口下界 |
| `min_units/max_units` | 拆分与槽位数；M2 的区域/路线拆分不读上限，已修正 |
| `target` 多类型 | 区域/路线/点/目标列表；输出保留原始结构 |
| `constraints` | 地面 A* 绕行、风险评分、目标禁入区；空中仍直线 |
| `meta.cell_size_m` | 坐标/路径归一化；样例为 1 |
| `params.duration_s` | 槽位时长；基座 work 按参与成员 work_rate 折算 |
| `plan_version` | 当前固定 1；重规划由协调器维护 plan_id |
| `result_status` | `PLAN_ONLY`，不冒充成功 |
| `fires` / 毁伤 | 不在计划层；T-ASL 的打击与弹药由基座行为层执行，效果判定走 `assessment.py` |
| `to-v2` | 只做有损性检查并拒绝，不生成等价旧场景；运行视图走 `_meta.interop` |

边界：

- 计划层不含火力动作与效果判定；T-ASL 的打击、弹药和毁伤/压制/夺占结论由基座行为层与评估接口产生；
- 不发布 ROS、不启动 Gazebo、不写运行终态；
- 任务段动作（巡逻绕环、侦察覆盖、封控拦截、坚守换班）仍由基座行为层接管；
- `motion=real` 是基座运动替身，不是 interop A* 路径跟随；
- 能耗/风险系数是演示值，不能当装备实测。

## 16 复核结论

- 当前样例 `mixed_inspection`：4/4、9/9 槽位、0 冲突、makespan 210 s；工作台逐步运动 4/4、212 s。
- `plan.json` / CSV / report / manifest 与 `interop` 计算一致；`ros2_commands.txt` 与 `commands.csv` 同源。
- 工作台 `interop_neutral` 运行会同时保存 4.2 计划包与反馈轨迹，两者来源分开标注。
- 未验证：真实 ROS/Gazebo 发布、真实导航控制器、T-ASL/效果链、外部平台联调。
