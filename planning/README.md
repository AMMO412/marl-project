# planning —— 任务规划中间层最小流程原型

把「编组输入 → 规则规划 → 下发计划 → 执行反馈 → 偏差判定 → 重规划」这条链跑通。
**不含任何强化学习**，这是方案里的 V0 链路 + V1 规则基线骨架。

---

## 一、先理解一次循环在干什么

不是「把输入算成输出」的一次性函数，而是一个**滚动循环**：

```
t=0    规划出覆盖 [0, 20] 的计划（H=20）
t=0..4 只执行开头 5 步（K=5）
t=5    丢掉后 15 步，重新规划覆盖 [5, 25]
       期间若发生成员损失 / 偏差超阈值 → 不等 K 步到期，立即重规划
```

计划之所以要算 H=20 步那么长，是为了让**排程看到更远**（避免把作业排进死胡同），
不是为了让下面照着执行到底。每次真正被采纳的只有开头 K 步。

**规划器内部 6 步**（`planner.py` 的 `plan()`，每一步都往 `events` 里留痕）：

1. **能力过滤** —— 剔除不可行的 (平台, 作业) 组合。V1 只启用续航与载荷
2. **代价打分** —— 按当前优化目标（makespan / dispersion / energy）
3. **分配求解** —— 满足 `crew>=N` 的前提下指派，贪心
4. **时序排程** —— 排入时间窗，协同作业要等人齐
5. **冲突消解** —— 平台时间重叠就串行后移；凑不满人就本轮放弃；超时间窗就放弃
6. **输出校验** —— **整份方案**再过一遍能力约束，抓「单条合法但叠加超续航」

第 6 步是关键：单条指派合法 ≠ 整份方案合法。

## 四、两个已经踩过的坑（改代码时别退回去）

**坑 1：滚动时域把开工时间一遍遍往后推。**
表现：作业一个都完成不了，每次重规划 start 都 +K。
两个原因，都已修：
- 排程用总工作量，而不是**剩余**工作量 → `planner._remain()`
- 重规划不继承上一版已发出的指派 → `planner.KEEP_COMMITMENT`

想复现这个故障：把 `KEEP_COMMITMENT` 改成 `False` 再跑一次。

**坑 2：平台位置从不更新。**
表现：到达时间每次都一样，而 `now` 在往前走，开工时间被无限推迟。
已在 `executor.py` 里于开工时把平台位置更新到作业点（原型简化：开工即到位）。

**坑 3：EDF 装错位置，代码能跑但结果一点不变。**
一度把「截止最早先干」装在**分配**那一步，实测四组配置结果完全相同。
原因：贪心分配允许一台平台被多个作业占用（顺序执行），**分配阶段不存在抢资源**，
真正的竞争在**排程**阶段。装错位置不会报错，只会静默无效。

**坑 4：命令行开关把模块默认值悄悄覆盖。**
写成 `planner.X = not a.no_x` 时，"不传参数"会被强制设成 True。
正确写法是 `default=None`，不指定就不改模块默认值（`--urgency` / `--no-urgency` 成对）。

## 四之二、排不进时间窗怎么办（第 5 步的消解手段）

消解手段按顺序试，代价从小到大：

1. **`add_crew` 加人** —— 协同作业效率是各成员之和，多一台干得快
2. **`swap_crew` 换人** —— 换成更近、更快的平台
3. **`defer` 上报** —— 穷尽手段仍无解，标记为 `need_report`

> **为什么必须有"换人"**：加人只能缩短**工期**，缩短不了**路上的时间**。
> 最近的平台赶过去就要 43 步、窗口只剩 30 步时，加多少人都没用，只能换更近的。
> 换人同样只从 `feasible_pairs` 里挑，不会突破能力约束。

**"放弃"本身不是问题，"静默放弃"才是。** 现在 defer 会标记 `need_report`，
统计里单列一行 `需上报上层`，由上层决定放宽窗口 / 增派资源 / 正式放弃。
中间层不该自己偷偷决定"这个活不干了"。

实测（6 seed × 60 步，H=20，2026-10-23 重测）：**换人开与关结果完全相同**
（完成 24 vs 24）。即换人在当前场景下**没有收益**，但逻辑正确、也无害，所以保留。

> **曾误报过「换人 +5.2pp」——那是 bug 制造的假象。**
> 加人/换人最初计算开工时刻时用了 `now + 路上时间`，
> 把第 5 步刚做好的串行错峰**撤销**了，于是作业"看起来"排进了窗口，
> 实际是产出「一台平台同时干两个活」的**重叠非法计划**。
> 已修：这两个函数现在接收 `earliest`，必须继承串行化的结果。
> 修完换人的收益归零，消解率也从虚高的 61.5% 回落到真实的 52.3%。
>
> **教训：指标突然变好，先怀疑是不是引入了非法解，而不是急着庆祝。**

> **EDF 默认关，实测是负优化**：消解率涨了但完成数掉 4 个，
> 把仿真延到 120 步也追不回来——不紧急的作业被反复挤出规划视野（饿死）。
> 开关保留是为了让结论可复现，不是当默认。

**已知缺陷「短视」（`tests/test_myopia.py` 可复现）**：
一台平台面对「A 近但不急（代价 14）」和「B 远但很急（代价 15、窗口 20）」时，
贪心先派 A，把 B 挤到完工 24 > 窗口 20 → B 失败。
而正确做法是先 B 后 A，**两个都能成**。
修法属于 WP1：代价函数要看得见"后面还有什么、有多急"。

诊断工具：`python tests/diag_window.py --now 40`，能看到每个作业的时间窗、
候选平台的到达步数，以及"加人能不能救回来"。

## 四之三、规划视野 H 是这个原型最灵敏的旋钮

实测（6 seed × 60 步，makespan，**2026-10-23 能耗模型改版后重测**）：

| H | 完成数合计 | 消解率均值 | 方案级越界 |
| --- | --- | --- | --- |
| **20（默认）** | 24 | 43.4% | 5 |
| 30 | 33 | 51.2% | 12 |
| 45 | **36** | 64.7% | 22 |

**H 20→45：完成数 +50%，消解率 +21pp。** 影响远大于换人（+0）与 EDF（-4）。

**但 H 大不是没代价**：H=45 时会把更多活塞进同一份计划，
于是「单条合法、叠加超续航」的**方案级越界**从 5 次涨到 22 次。
第 6 步会**拦截**——检测到就撤下该指派，不再下发。
**宁可少干，也不能下发会半路没电的方案。**

> 上一版记的是「28 → 40」。能耗模型与续航闸门口径改了之后重测，
> 绝对值变了，**但结论方向没变**。历史数字别跨口径引用。

机理：作业的开工时间被前面排的活推到 40 步之外，一旦超过 `now+H` 就本轮不排。
H 太窄时，明明人手充足、时间窗也够，作业就是排不进去。

> 这与 2.2（3）的"20 回合"是**两回事**：H 是规划视野，"20 回合"是消解时限，
> 别混为一谈。H=20 是**我方暂定**（会议一·42 只是举例"10 步或 20 步"）。

有作业因超出视野被跳过时，统计会自动打印警告。想对照：`--H 45`。

**看瓶颈要按"作业数"而不是"拒绝次数"**：`派不出去的原因分布` 里
`续航不足` 条数天然最多（它是按 平台×作业 组合计的），不能直接拿来定位瓶颈。

## 五、怎么读这些数字（每次引用前先看这一节）

### 5.1 每个数字能不能当验收证据

| 数字 | 能不能当验收证据 | 说明 |
| --- | --- | --- |
| 完成 / 失败 / 未结束 作业数 | **内部相对比较** | 只用来看流程通不通、策略有没有效果 |
| 冲突发现次数、消解次数 | **不能** | 冲突定义是我们自己定的；**每次重规划会把同一件事重复计数**，不是文档 2.2（3）的口径 |
| 方案级越界 0 次 | **不能** | 只说明「续航+载荷这两类」没越界。传感器、运动性能**尚未启用**（统计里显式列出） |
| 偏差触发次数 | 内部观察 | 阈值 4.0 是拍的，不是测的 |
| 需上报上层 | **要拿去问甲方** | 本层穷尽手段仍无解，属于需要上层拍板的事项 |
| **每完成一个作业的能耗** | 内部相对比较 | 已按完成数归一化。但**完成数不一致时仍可能只是"少干活"**，必须先看完成数 |
| **完成时刻（makespan）** | 内部相对比较 | 只在**完成数可比**时才有意义。干得少的策略天然收尾早 |
| **分散度** | 内部相对比较 | 到质心平均距离。**完成数少 → 平台少移动 → 更接近初始分散度**，这是混淆项 |
| **crew=1 最优 vs 贪心** | 参考 | 同一可行域下比。默认场景实测差 0（见 5.4） |
| **重规划触发源计数** | 内部观察 | 四类各自独立。同一轮可命中多类，所以各类之和 > 规划次数是正常的 |

> 一句话：**这套东西证明的是「链路能跑通」，不是「指标已达标」。**

### 5.2 三条"看起来变好、其实是假象"的陷阱

1. **不要比总能耗。** 干得少的策略天然更省电，那是"少干活"不是"更省电"。
   必须按完成数归一化成"每作业能耗"。
2. **完成时刻要对齐完成数。** energy 目标的完成时刻比 makespan 还低（34.0 vs 35.8），
   因为它只完成了 26 个作业、而 makespan 完成了 33 个——收尾早是因为**干得少**。
3. **分散度要对齐完成数。** 一个作业都没干时，分散度 = 初始分散度（实测 seed0：
   energy 完成 0 个，分散度 33.61，与初始 33.61 完全相同）。

**怎么破：先让完成数持平，再比指标。** dispersion 目标就是这么调出来的
（`W_TIME_DISP=1.0` 使它与 makespan 同为 33）。

### 5.3 三类优化目标怎么比（对应 2.3（4））

| --- | --- | --- | --- |
| 0 | 4 / 37 / 30.82 / 34.70 | 4 / 48 / 35.86 / **35.44** | 3 / 37 / **28.88** / 32.62 |
| 1 | 5 / 52 / 48.29 / 40.79 | 5 / 44 / 51.40 / **41.55** | 4 / 54 / **46.88** / 37.56 |
| 2 | 3 / 28 / 21.42 / 36.86 | 3 / 34 / 25.42 / **39.42** | 3 / 39 / 23.64 / 37.84 |
| 3 | 4 / 32 / 40.51 / 33.14 | 4 / 32 / 40.51 / 33.14 | 2 / 23 / **13.74** / 37.66 |
| 4 | 5 / 29 / 24.48 / 37.50 | 5 / 36 / 27.65 / **37.88** | 4 / 29 / **20.48** / 38.53 |
| 5 | 3 / 33 / 28.57 / 43.95 | 4 / 38 / 35.18 / **46.47** | 2 / 23 / **25.34** / 43.20 |
| 6 | 4 / 40 / 29.60 / 32.99 | 3 / 35 / 26.41 / **36.48** | 3 / 31 / **22.11** / 35.32 |
| 7 | 5 / 35 / 26.81 / 35.38 | 5 / 49 / 28.72 / **38.32** | 5 / 36 / **21.61** / 37.10 |
| **合计/均值** | **33** / 35.8 / 31.31 / 36.92 | **33** / 39.5 / 33.89 / **38.59** | **26** / 34.0 / **25.34** / 37.48 |

（每格：完成数 / 完成时刻 / 每作业能耗 / 分散度）

**分化结论（可复现，`python analyze.py --seeds 8` 会重打这张表）：**

| 判定 | 结果 | 能不能信 |
| --- | --- | --- |
| dispersion 的分散度 > makespan | **7/8 seed** | **能信**：两者完成数持平（33 vs 33），无"少干活"混淆 |
| energy 的每作业能耗 < makespan | **7/8 seed** | **要打折**：完成数只有 26/33（79%） |
| makespan 的完成时刻 < dispersion | 5/8 seed | 能信：完成数持平，35.8 vs 39.5 |

三个已经踩过的坑：

1. **不要比总能耗。** 见 5.2。
2. **dispersion 必须传拥挤度参数。** 之前 `_cost()` 的 `crowded` 一直是默认 0，
   导致 dispersion 退化成 makespan，两个目标结果一模一样。已在 `planner.py` 修。
3. **能耗系数不能定成"快的更省"。** 第一版把 `move_cost` 定成与速度反相关，
   结果 energy 与 makespan 永远选同一台平台——seed0 两个目标成绩单**一模一样**。
   物理上也是反的（功率随速度上升）。改成 `move_cost = 0.5×speed²` 后才分化。

### 5.4 分配求解器：最优 vs 贪心

`crew=1` 的作业走**一对一最优指派**（匈牙利）；`crew>1` 保留排序补位
（一个作业要 N 台，已经不是一对一，硬套会丢可行解）。

每次规划都会在 `events` 里留一条 `assign_solve`，`run_flow` 末尾打印合计：

```
crew=1 指派求解（共 26 轮，求解器 内置JV）：最优合计 1420.0，贪心合计 1420.0，差 0.00（0.0%）
```

**默认场景（15 平台 8 作业）实测差距为 0%** —— 平台远多于 crew=1 的作业，
贪心随便挑都不会撞车。**这不代表求解器没写对，只说明这个场景太宽松。**

资源紧张时差距才出现（`python tests/diag_solver.py`，4 seed × 60 步）：

| 平台 × 作业 | 求解轮数 | 最优合计 | 贪心合计 | 差距 |
| --- | --- | --- | --- | --- |
| 15 × 8（默认） | 26 | 1420.0 | 1420.0 | **0.0%** |
| 6 × 8 | 40 | 2535.0 | 2571.0 | +1.4% |
| **3 × 8** | 37 | 2906.0 | 3134.0 | **+7.8%** |

求解器：优先 `scipy.optimize.linear_sum_assignment`，没装就用自带的 JV 实现
（`planner._hungarian_stdlib`，纯标准库 O(n³)）。**自带一份是必须的**：
交付环境不支持外网（一·19），不能假设目标机装了 scipy/numpy；
开发机（Windows 侧）也没有。两者结果在单测里互校（用例 13，没装 scipy 时 SKIP）。

### 5.5 重规划触发源（四类各自独立）

```
重规划触发源（各自独立，同一轮可多条）：
    init           首次规划   1 次
    member_change  成员变化   1 次
    exec_fail      执行失败   0 次
    timeout        超时     0 次
    deviation      偏差超阈值  0 次
    periodic       滚动周期   11 次
```

为什么要拆开：原来用的是一个 `reason` 字符串，同一步里同时发生
"成员损失 + 执行失败 + 超时"时**只有最后一个被记下来**，另外两个被吃掉。
现在每类独立计数、独立留痕，`flow_trace.jsonl` 的每条 trace 都带 `triggers` 字段。

> 各类次数之和 **大于**规划次数是正常的——一次规划可以有多个理由。

### 5.6 关于 OR-Tools CP-SAT（WP1 的决定：**暂不引入**）

WP1 原计划"带约束排程上 OR-Tools CP-SAT（crew≥N、时间窗、先后关系）"。
做完上面的对照后，**决定这一轮不引入**，理由与触发条件是：

| # | 理由 | 依据 |
| --- | --- | --- |
| 1 | **交付环境不支持外网**（一·19），引入就多一个必须随包安装的二进制依赖 | 会议纪要 |
| 2 | **当前规模下没有收益**：crew=1 的最优 vs 贪心在默认场景差 0%，只有资源紧张到 3 平台×8 作业才差 7.8% | `tests/diag_solver.py` 实测 |
| 3 | **它解决的那部分约束我们已经有了替代手段**：crew≥N 用排序补位，时间窗用加人/换人/defer 三级消解 | `planner.py` 第 3/5 步 |
| 4 | **引入了也没法验证**：WSL 环境没装 ortools，装不上就等于写了一段没人跑过的代码 | 环境事实 |
| 5 | 代价是**真金白银的排程质量**，但那要等 WP2 有了真实移动与能耗之后才量得出来 | 排期 |

**重新评估的触发条件**（满足任一就重开这个议题）：
- 作业数上到 30+ 且出现**先后关系**（precedence）约束——这是贪心与匈牙利都表达不了的；
- 甲方给出真正的"消解时限"口径，需要按硬截止做可行性证明；
- 资源紧张场景变成常态（平台/作业 < 1）。

**备用材料**（未启用、未在本环境验证）：见 `docs/ortools_cpsat_备选.md`，
里面有安装命令与最小示例，届时照抄即可。

### 一条重要经验：回归必须有一个「必现」的触发点

回归全绿，但 bug 还在。补到 2 平台 6 作业**仍然触发不到**。

> `1 串行不变量 FAIL：P1: (2,14,'A') 与 (5,15,'B')`，退出码 1。
