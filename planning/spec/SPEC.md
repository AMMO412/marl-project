## 二、平台与单位

| 项 | 暂定 | 说明 |
| --- | --- | --- |
| 时间 | 无量纲"步" | 1 步 = 1 个决策周期。真实系统落地时换成秒 |
| 距离 | 无量纲坐标单位，场景 100×100 | |
| 能耗 | **电量单位**（不是步数）。闸门、记账、择优三处同口径 | 参数到位后换算成焦耳 |
| 载荷 | 无量纲 | |

四类平台（一·32：坦克、无人战车、两类固定翼无人机；一·33 用公开参数，做成可配置项）：

| 代号 | 对应 | speed | work_rate | battery | payload | sensor | move_cost | work_cost |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `tank` | 坦克 | 1.0 | 1.2 | 120 | 8.0 | eo | 0.5 | 1.44 |
| `ugv` | 无人战车 | 0.8 | 1.0 | 100 | 6.0 | eo | 0.32 | 1.0 |
| `uav_a` | 固定翼无人机A | 2.0 | 0.6 | 60 | 2.0 | sar | 2.0 | 0.36 |
| `uav_b` | 固定翼无人机B | 1.6 | 0.5 | 80 | 1.5 | ir | 1.28 | 0.25 |

> 这些是**公开近似值**，只为让流程能跑。不是任何真实装备的参数。

能耗系数怎么定的（**我方暂定**，WP1 引入）：

```
一次指派的预计耗电 = 移动步数 × move_cost + 作业步数 × work_cost
      move_cost = 0.5 × speed²        → 移动能耗 = 0.5 × 距离 × speed
      work_cost = 1.0 × work_rate²    → 作业能耗 = 1.0 × 工作量 × work_rate
```

**"跑得快更费电、干得快也更费电"**，这是刻意与完工时间反向的。
第一版我把系数定成"快的更省"，结果 `energy` 与 `makespan` 永远选同一台平台——
实测 seed0 两个目标的成绩单**一模一样**，区分度为零。物理上那也是反的
（功率随速度上升、随吞吐上升）。真实数据到了只需改这 8 个数。

## 三、场景文件格式（`taskalloc-scenario/v1`）

```json
{
  "format": "taskalloc-scenario/v1",
  "version": 1,
  "step": 0,
  "objective": "makespan",
  "platforms": [
    {"pid":"P00","ptype":"tank","pos":[12.3,45.6],
     "battery":120,"payload":8.0,"speed":1.0,
     "work_rate":1.2,"sensor":"eo","alive":true}
  ],
  "tasks": [
    {"tid":"T00","ttype":"patrol","pos":[70.1,20.5],
     "work":12,"window":[0,60],"crew":1,
     "need_payload":0,"need_sensor":"eo",
     "progress":0,"status":"open"}
  ]
}
```

用法：

```bash
python run_flow.py --save-scenario spec/sample_scenario.json   # 生成
python run_flow.py --scenario spec/sample_scenario.json --steps 40   # 加载并跑
```

**验收点**：换场景只换文件，不改代码。已验证——文件加载与同 seed 直接生成的结果完全一致。

## 六、三类优化目标（2.3（4））

代价函数是四项加权和（我方暂定，`planner.COST_TERMS`）：

| 项 | 含义 |
| --- | --- |
| `time` | 完工所需步数 = 移动步数 + 作业步数 |
| `energy` | 预计耗电 = 移动步数×move_cost + 作业步数×work_cost |
| `spread` | 分散度损失 = (平台到质心距离 − 作业到质心距离)/50，为负=让编队更分散 |
| `crowd` | 聚集惩罚 = 作业点 30 半径内的存活平台数 / 存活平台总数 |

| 目标 | time | energy | spread | crowd | 观测指标 |
| --- | --- | --- | --- | --- | --- |
| `makespan` 任务完成时效 | 1.0 | 0 | 0 | 0 | 完成时刻 |
| `energy` 能耗代价 | 0.3 | 1.0 | 0 | 0 | 每完成作业的能耗 |
| `dispersion` 战场暴露风险 | 1.0 | 0 | 20.0 | 10.0 | 分散度（到质心平均距离） |

> 两个非 1 的权重是**扫描出来的，不是拍的**（8 seed × 60 步）：
> - `energy.time=0.3`：取 0 时 seed0 一个作业都完不成，完成数只有 makespan 的 36%；
>   取 0.3 后回到 79%，每作业能耗才谈得上可比。
> - `dispersion.time=1.0`：使 dispersion 的完成数与 makespan **持平**（33 vs 33），
>   于是"分散度更高"不能再被解释成"干得少所以没聚拢"。
>   取 0.2 时完成数 17/8seed，分散度虽更高，但那是少干活的假象。

> **暴露风险用"分散度"作代理**，不是真实的战场暴露风险。这一点不能含混。

## 六之二、强化学习的奖励函数（暂定）

`rl/learn_weights.py` 用的奖励：

```
奖励 = 100×完成作业数
     − 0.3×总能耗
     − 5×冲突实例数
     − 50×方案级越界次数
     + 50×20步窗口内消解率
```

**这一条决定了"什么叫好的决策"，必须由甲方确认后才算数。**
当前它偏向"多完成"，能耗权重偏小（0.3）——这也是为什么学习结果主要压能耗。
如果甲方更看重时效，系数要整体重定。

被学的对象是 6 维权向量（移动时间/作业时间/能耗/拥挤度/载荷余量/续航余量），
见 `planner._features()`。学习只改偏好，不改能力约束。

## 七之二、补给相关（思路已验算，功能暂不实现）

「差一点点就派不出去 → 先补给再出发」在真实系统成立（返航充电、补给后出动）。
验算结果（`tests/diag_refuel.py`）：当前场景下 8 个作业在 t=0 **全都有直达可行的平台**，
一个都不需要补给 → **暂不实现**，不为不存在的问题加代码。

但要真做补给，有三个甲方未给的参数，**且其中一个是语义问题**：

| 项 | 暂定 | 风险 |
| --- | --- | --- |
| 补给点位置 | 场景中心 (50,50) | 真实部署有多个补给点，位置未知 |
| 补给耗时 | 5 步 | 未知 |
| **`payload` 语义** | 见下 | **代码里两处注释不一致** |

> **关键：`payload` 是"剩余挂载量"还是"固有载重能力"？**
> - `contract.py:23` 写"载荷"，`contract.py:62` 写"剩余载荷"
> - 若是**消耗品**（挂载余量）→ 补挂能解决，`载荷不足` 可用补给消解
> - 若是**固有能力**（载重上限）→ **补给补不出来**，只能换平台
>
> 这个语义不定，`载荷不足` 的消解手段就定不下来。**须向甲方确认。**

补给不是免费的：绕路 + 补给耗时 + 开工推迟，可能把作业挤出时间窗。
**是否划算必须算，不能凭直觉**（`tests/diag_refuel.py` 就是干这个的）。
