# 系统改进设计 V2：对着新要求，planning 还能不能用

V0.1 ｜ 2026-10-24 ｜ 依据《五类作战任务_图文版》《机器人移动话题说明》《四类平台参数指标与 Gazebo 实现详尽调研》

---

## 0 结论先行

**能用，但只能当"链路原型"。** 六步规划内核（过滤→打分→分配→排程→消解→校验）本身没有被新文档推翻，仍然成立，且已有实测基线与回归兜底，**不要推倒重来**。

但要对着新要求当验收对象，**缺四层**。其中第一层已经补上：

| 层 | 缺什么 | 状态 |
| --- | --- | --- |
| **判据层** | 只有 `progress >= work`，而新文档要求 7 态状态机 + 判据五要素 + 全过程检查 | **已落地 `criteria.py`** |
| 执行层 | 下游只有速度指令，我们的"开工即到位"不成立；RTF≠1 使开环不成立 | **已落地 `bridge.py`**（未联调） |
| 状态层 | 缺"结果待确认""已解除"两个状态 | 在 `criteria.py` 里已定义，待接入主链路 |
| 证据层 | 判据要"证据 + 缺失处理"，我们没有独立证据记录 | 待做 |

**还有一条必须写在最前面**：平台参数调研的核心结论是——

> "现有 50 路 cmd_vel **尚不能证明模型具备某一真实平台的最大速度、载荷、续航或飞行能力**。参数要经过模型、控制插件或能源逻辑实际执行，并用反馈数据核验。"

**这意味着我们能力闸门用的速度、载荷、续航、传感器四项，目前全部没有真实来源。** 这不是"精度不够"，是"输入不存在"。设计上必须把能力做成**可注入、可标注来源**的形式，否则以后拿到的数也会和暂定值混在一起。

## 1 三份新文档带来的硬约束

### 1.1 《五类作战任务_图文版》

| 要求 | 对我们的直接影响 |
| --- | --- |
| 状态分 **7 种**，含**"结果待确认"** | 我们只有 open/running/done/failed，**缺两个状态** |
| 一项判据必须写清**五件事**：对象 / 时间 / 门槛 / 证据 / 缺失处理 | 我们一个都没有，只有"工作量"一个数 |
| **全过程要求不能只检查最后一帧** | 我们正是只看 `progress` 是否达标——典型最后一帧 |
| 持续型任务（巡逻/封控/坚守）需覆盖**整个时段记录**，尤其状态变化时刻 | 我们没有时间序列记录 |
| **完成条件**（合不合格）与**优化指标**（哪种更好）分离 | 我们现在混在奖励函数里（完成数直接进 reward） |
| **0 次事件不能写成 100%**；缺日志 ≠ 零事件 | 我们的消解率、完成率都有这个问题 |
| 巡逻：最大重访间隔**含首尾等待**；有效访问 ≠ 路过 | 判据要改 |
| 封控：**到位≠控制、发现≠阻止、无目标≠能处置** | 到位不能给成功 |
| 侦察：合并覆盖率是**并集不是相加**；分母固定；必查项独立于总量门槛 | 判据要改 |
| 突击：**预测概率 ≠ 已发生的结果**；结果须由评估反馈确认 | 不写概率判据 |
| 坚守：**最后一帧和平均值不能代替全过程**；轮换要记接替时刻 | 判据要改 |

### 1.2 《机器人移动话题说明》+ 平台参数调研

| 事实 | 影响 |
| --- | --- |
| 只有 Twist，**没有"到达目标点"** | 任务级 → 速度级 缺一层，我们补（`bridge.GoalController`） |
| Twist **没有 Header**：无时间戳、坐标系、目标点、持续时间、**载荷、续航** | 位姿以外的一切都要自己维护 |
| RTF 不确定，"速度×秒数"推不出位移 | 只能闭环，不能开环定时 |
| **无超时自动停车**；一台机器人只一个发令源 | 停止必须显式发；重规划不能新开发布器 |
| 飞机 VelocityControl **不会因有电池而自动禁飞**；耗电可能绕过触发路径 | "电量耗尽即停"不成立——**我们的电池模型目前是自己记账** |
| 图像**尚未发布为 ROS 2 Image 话题** | `sensor`（eo/ir/sar）**没有真实数据来源** |
| 速度/载荷/续航**均未被证明** | 能力闸门无真实输入 |

## 2 现状体检：对着原来的四组指标

| 指标 | 我们现在做到哪 | 判定 |
| --- | --- | --- |
| **2.1** 订阅编组、接收时延 ≤50ms | 输入是 `sample_scenario()` 自己造的，**没有订阅** | **要改**：换成订阅式输入。但 50ms 从何时计到何时、跨机时钟怎么对齐，原文未定 |
| **2.2** 每平台的子任务 / 时序 / 时间窗 / 协同约束 | `Assignment` 四类字段齐全 | **能用** |
| **2.2** 20 回合内冲突消解率 ≥95% | 有自己的消解率，但**口径未定且跨轮重复计数** | **不能当证据**（口径问题，不是数值问题） |
| **2.3** 不少于 5 类任务规划解析 | 五类参数齐，能规划 | **部分**：规划能跑，但**判据不是五类各自的** → `criteria.py` 已补 |
| **2.3** 不生成超出能力边界的方案 | 续航+载荷两条已启用、第 6 步方案级拦截 | **不能用**：四项能力参数**全部无真实来源**（调研文档结论） |
| **2.4** 双引擎对接 / 可视化 / 评估 | `flow_trace.jsonl` 有完整留痕；**无独立评估模块** | **部分**：留痕够，评估模块缺 |

> 一句话：**输出格式对得上，判据和能力两处对不上。**

## 3 改进后的系统结构

```
上层编组 ─┐
想定/导调 ─┴→ [L1 契约层 contract]     数据结构 + 能力提供者（可注入、带来源标注）
                    ↓
              [L2 规划内核 planner]    六步：过滤→打分→分配→排程→消解→校验  ← 基本不动
                    ↓  Assignment（子任务/时序/时间窗/协同约束）
              [L3 判据层 criteria] ★新增  7 态状态机 + 五类判据 + 全过程检查
                    ↓  Verdict
              [L4 执行适配 bridge] ★新增 目标点 → Twist 闭环；位姿解析；发令纪律
                    ↓  cmd_vel
                下游 ROS 2 / Gazebo / UE5
                    ↓  位姿与事件
              [L5 证据层 evidence] ★待做  按"对象/时间/门槛/证据/缺失处理"记全过程
                    ↓  Evidence 序列
                 回到 L3 判定
```

**关键点：L2 规划内核基本不动。** 它做的是"分配 + 排程 + 消解"，这部分新文档没有推翻。改动集中在它的上下游。

---

## 4 各层怎么改

### L1 契约层 `contract.py`

| 改动 | 说明 |
| --- | --- |
| 加 `CapabilityProvider` | 能力参数（速度/载荷/续航/传感器）改为**可注入**，每个值带 `source`（暂定 / 实测 / 下游给定）与 `verified` 标记。调研文档说参数必须"实际执行并用反馈核验"，所以来源不是元数据，是判据的一部分 |
| `Task` 加 `shape` | 支持 point / circle / polygon / polyline，默认 point 向后兼容。这是封控与侦察判据的**输入前置** |
| `Task` 加 `criterion` | 判据五要素配置（对象、时间、门槛、证据、缺失处理），挂到 `criteria.Criterion` |
| `Platform` 加 `yaw` | 下游是差速驱动，有朝向；我们现在没有 |

### L2 规划内核 `planner.py`

| 改动 | 说明 |
| --- | --- |
| 到达时间不再"一步到位" | 下游需先转向再前进，且 RTF 不确定 → 到达时间改为**估计值 + 不确定度**，排程要留余量 |
| 能力闸门改成问 `CapabilityProvider` | 不再直接读 `PLATFORM_SPECS` |
| **不判完成** | 完成判定交给 L3。planner 只产出"谁在什么时候去哪" |

> 其余（匈牙利、加人/换人/defer、方案级校验）**不动**——这些已有实测支撑。

### L3 判据层 `criteria.py`（**已落地**）

- **7 态状态机**：`open / running / pending_confirm / success / failed / timeout / released`；失败与超时**分别记录**
- **判据五要素**配置：`Criterion(objects, mandatory, t_start, t_end, confirm_deadline, threshold, need_kinds, on_missing)`
- **五类判据函数**，全部吃**全过程记录**而非当前值：
  - `judge_patrol`：最大有效重访间隔，**含开头与结尾等待**；无历史时另记首次期限，不虚构已访问
  - `judge_blockade`：控制状态时间线 + 禁止事件 + **事件闭合**；防住"到位≠控制""发现≠阻止"；缺记录 → 待确认
  - `judge_recon`：**并集**覆盖（重叠只算一次）+ 必查项独立核对 + 回传确认
  - `judge_assault`：**不算概率**；只看执行记录 → 结果确认 → 关联正确 → 期限合格
  - `judge_hold`：全时段在位下限（**逐时刻检查，不是最后一帧**）；轮换记接替时刻
- **纪律内建**：`unknown ≠ false`。缺证据一律 `pending_confirm`，绝不默认合格

自测 15 例，全部与《图文版》示例结论一致：

```
巡逻 0/8/17/26 → success    巡逻 0/8/22/29 → failed（等了 14）
巡逻 中途(20)  → running    巡逻 无任何记录 → pending_confirm
侦察 并集90未回传 → pending_confirm      侦察 +回传 → success
侦察 缺必查u95 → failed      侦察 补上u95 → success
坚守 丙第9到位 → success      坚守 丙第11到位 → failed（第10时刻只有1台）
封控 记录完整 → success       封控 缺第7时刻 → pending_confirm
封控 有禁止事件 → failed
突击 执行未确认 → pending_confirm  超确认期 → timeout  结果确认 → success
```

### L4 执行适配 `bridge.py`（**已落地，未联调**）

50 台编成与话题映射、类型映射、`Twist`、`Pose`、**闭环 `GoalController`**、单位换算、发令纪律。自测：无人车走 20 米 **97.5 秒**、飞机带高度 **29.9 秒**。

### L5 证据层（**待做**）

`evidence.py`：把执行过程中产生的访问、观测、在位、事件、结果、回传统一记成 `Evidence(kind, at, source, obj, value, valid)`，按任务编号与规则版本归档。

这一层是**判据层能工作的前提**——L3 吃的就是它。也是 2.4"评估"的落点。

## 5 分阶段路线

| 阶段 | 内容 | 依赖 | 可验收 |
| --- | --- | --- | --- |
| **P0** | L3 判据层接入主链路：executor 产出 Evidence → criteria 判定替身状态；状态机 7 态替换 open/done | 无 | 五类判据单测 + 回归不退化 |
| **P1** | L5 证据层 + 全过程留痕；`flow_trace.jsonl` 增加 Evidence 序列 | P0 | 能重放任一任务的全过程并复算判定 |
| **P2** | L1 `shape` 字段 + 能力提供者；封控/侦察判据拿到输入 | P1 + 甲方给几何口径 | 封控、侦察判据不再是空转 |
| **P3** | L4 接真下游：闭环到位、显式停止、单一发令源 | 下游速度上限 + 场地尺度 | 位姿闭环收敛；停止命令有效 |
| **P4** | 能力参数标定（速度/续航/载荷/传感器）后**一次性重测**全部基线 | 下游实测数据 | 三目标分化、H 扫描、消解率全部重打 |

> **P4 之前不要改 `PLATFORM_SPECS` 的数值。** 改了会让现有全部实测数字作废，而参数还没确认，很可能改两次。

## 6 对原指标可测性的影响

| 指标 | 现在 | P0–P2 后 | P3–P4 后 |
| --- | --- | --- | --- |
| 2.1 接收时延 | 无订阅，不可测 | 有订阅后可测（口径仍待定） | 同左 |
| 2.2 四类输出 | **可测** | 可测 | 可测 |
| 2.2 消解率 95% | 口径未定，不可当证据 | 有 Evidence 后可重算 | 口径定后可对 |
| 2.3 五类解析 | 规划可跑，判据不合格 | **五类判据各自成立** | 同左 |
| 2.3 不越界 | **参数无来源，不可当证据** | 结构就位，仍无真实参数 | 标定后可测 |
| 2.4 评估 | 有留痕，无评估模块 | **判据即评估** | + 双引擎实测 |

## 7 待确认（按卡住程度排序）

1. **能力参数什么时候能给？** 速度上限、续航、载荷、传感器——**四项全无来源**，能力闸门目前是自说自话。
2. **封控要哪一层？** 边界监测 / 通行控制 / 主动处置 / 持续维持（图文版说这四层**不能互相替代**）。
3. **侦察的"回传确认"由谁确认？** 判据需要接收方的确认记录。
4. **突击的"结果评估"由哪个模块出？** 判据依赖它，没有就永远停在 `pending_confirm`。
5. **"有效访问 / 有效在位"的门槛怎么定？** 到达多近、持续多久算有效？
6. **允许中断多久？** 持续型任务的中断时长与次数规则——不写清楚，轮换就没法判。
7. **20 回合与消解率口径。** 老问题，仍未解决。
8. **场地尺度与规划步长。** 决定全部时间计算。
