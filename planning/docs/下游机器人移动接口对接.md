# 下游机器人移动接口对接：要改什么

V0.1 ｜ 依据下游《机器人移动话题说明》（GazeboUEBridge，50 台） ｜ 2026-10-24

> 本文只做一件事：把下游接口和我们 `planning/` 的现状逐条对照，列出**要改什么、改在哪、卡在哪**。
> 已落地的代码见 `bridge.py`（新增，零风险）。**本文所有【我方暂定】项均未经下游确认。**

---

## 0 结论先行

1. **下游没有"到达目标点"接口。** 只有速度指令（Twist）。我们下发的是任务级指令，中间缺一层"目标 → 速度"的翻译。**这层必须我们补**（`bridge.py` 已写，未联调）。
2. **我们的速度参数和下游不是一个量级。** 按下游的示例速度算，我们的到达时间**普遍偏乐观 2–5 倍**——这不是精度问题，是作业会大面积超时窗。
3. **平台类型、数量、编号、坐标系全部对不上。** 需要一层映射，且**映射会改变平台类型**（下游按号段固定划分）。

还有一条藏在说明第 4 节里、很容易漏掉的：

> "速度按仿真时间生效，`Seconds` 按墙钟时间计算。例如 RTF 低于 1 时，不能用'速度 × 实际发令秒数'推算实际位移。"

**这意味着开环定时发指令根本到不准，必须闭环读位姿。** 所以中间的翻译层只能做成闭环控制器，不能做成"发 N 秒当到达"。

## 1 下游接口要点（摘录）

| 项 | 下游给定 |
| --- | --- |
| 机器人 | **50 台固定编成**：UGV 01–20（20）、TANK 21–30（10）、PLANE 31–40（10）、WING 41–50（10） |
| 控制话题 | `/rover_XX/cmd_vel`，**每台一个话题**，不是广播/通配符 |
| 消息类型 | `geometry_msgs/msg/Twist` |
| 可用字段 | `linear.x`（前进，m/s）、`angular.z`（转向，rad/s）、`linear.z`（升降，**仅 31–50**）；其余恒为 0 |
| 位姿反馈 | `/model/rover_XX/pose`，`tf2_msgs/msg/TFMessage`，只读 |
| 坐标系 | **Z 轴向上**；`angular.z > 0` 为俯视逆时针；**不要套 UE 坐标符号** |
| 发令频率 | 约 20 Hz（0.05 s 一次），是发令频率，不代表位姿同步到 20 Hz |
| 停止 | **无超时自动停车**，必须显式发全零 Twist |
| 环境 | ROS 2 humble，`ROS_DOMAIN_ID=46`，`ROS_LOCALHOST_ONLY=1` |

**边界（说明第 7 节，直接决定我们能做到哪一步）：**

- 无人车/坦克是**差速驱动**，坦克只是履带外观，底层仍是差速轮代理
- 两类飞机是**关闭重力的刚体 + `VelocityControl`**，升降转向是简化运动控制，**不是油门或舵面指令**；无气动模型、失速、飞控、自动起降
- **当前没有"到达目标点""执行航线""自动避障"的任务话题或 Action**
- 同一机器人**只安排一个持续发令源**；另一程序持续发令时，单次停止命令可能被覆盖
- 地面机器人收到零速度后仍有短暂减速过程
- 图像**尚未发布为 ROS 2 Image 话题**

## 3 量化影响：速度必须重标定（这条最要命）

场景是 100×100，随机两点的**平均距离约 52 个场景单位**。按不同口径算"走过去要多久"：

| 口径 | ugv 走 52 单位 | uav_a 走 52 单位 |
| --- | --- | --- |
| **我们现在的模型**（speed 1.0 / 2.0，单位=步） | 52 步 | 26 步 |
| **下游实测速度**（0.2 / 1.0 m/s，1 单位=1 米） | **260 秒** | **52 秒** |

若 1 步 = 1 秒，下游走完全场要 **260 步**，而我们 `patrol` 的时间窗只有 **0–60 步**——**作业根本走不到**。

`bridge.py` 自测也印证了这个量级：无人车以 0.2 m/s 走 20 米，闭环收敛用了 **1950 拍 ≈ 97.5 秒**；同样距离飞机（1.0 m/s）用 **598 拍 ≈ 29.9 秒**。

### 建议标定（我方暂定，须下游确认速度上限）

取 **1 场景单位 = 1 米**（场景即 100×100 米，50 台分布合理）、**1 步 = 10 秒**：

| 项 | 现值 | 建议值 | 依据 |
| --- | --- | --- | --- |
| `M_PER_SCENE_UNIT` | — | **1.0** 米/单位 | 场景尺度；须问下游实际场地多大 |
| `SEC_PER_STEP` | — | **10.0** 秒/步 | 使 60 步窗口 ≈ 10 分钟，与 0.2 m/s 的地面速度相容 |
| `ugv.speed` | 1.0 | **2.0**（=0.2 m/s） | 下游示例默认 `Linear 0.2` |
| `tank.speed` | 1.0 | **2.0**（=0.2 m/s） | 同为地面差速，暂按同速 |
| `uav_a.speed` | 2.0 | **10.0**（=1.0 m/s） | 下游示例飞机 `Linear 1` |
| `uav_b.speed` | 1.6 | **10.0**（=1.0 m/s） | 同上 |

> 换算式：`speed[单位/步] = v[m/s] × SEC_PER_STEP ÷ M_PER_SCENE_UNIT`
>
> **注意这会改变平台间的相对快慢**：原来飞机是无人车的 2 倍，标定后变成 **5 倍**。
> 而 `recon` 需要 sar、`uav_a` 是唯一带 sar 的——飞机会明显变强，**三类目标的分化结果也要重测**。

### 我的建议：现在先别改 `PLATFORM_SPECS`

一旦改了，README 里所有实测数字（三目标 8 seed 成绩单、H 扫描、最优 vs 贪心）**全部作废**，而下游的速度上限还没确认——很可能改完还要再改一次。

正确顺序是：**先把换算常量做成可配置**（`bridge.py` 已做）→ **拿到下游的速度上限与场景尺度** → **一次性标定 + 一次性重测**。

## 4 已落地：`bridge.py`

新增文件，纯标准库，**不改任何既有行为**（没有 import 它的地方）。内容：

| 块 | 提供 |
| --- | --- |
| 编成与话题 | `FLEET_RANGES` / `build_roster()` / `topic_of()` / `pose_topic_of()` / `robot_no_from_pid()` |
| 类型映射 | `PTYPE_TO_KIND`（我们四类 → 下游四类，【我方暂定】） |
| 指令 | `Twist` dataclass + `to_dict()` + `stop()`；只发下游认的三个字段 |
| 位姿 | `Pose`（含 `yaw`，可选 `z`） |
| **闭环控制器** | `GoalController.update(pose, goal) -> Twist`，先转向后前进，`arrived()` 判到位 |
| 单位换算 | `scene_to_m()` / `steps_to_s()` / `M_PER_SCENE_UNIT` / `SEC_PER_STEP` |
| 发令纪律 | `CMD_PERIOD_S = 0.05`（约 20 Hz）+ 第 7 节的三条注意事项写进注释 |

自测（`python bridge.py`，无需 ROS）：

```
无人车直行：1950 拍到位（97.5 s），终点 (19.50, 0.00, 0.00)
无人车转向：2011 拍到位（100.6 s），终点 (0.00, 19.51, 0.00)
飞机带高度：598 拍到位（29.9 s），终点 (29.51, 0.00, 10.00)
```

**未联调**：控制增益（`DriveGains`）全是拍的，必须在真机/仿真里标定，不能当默认值交付。

## 5 待下游确认清单

按"不问清楚就没法往下做"排序：

1. **各类机器人的速度上限是多少？** 说明里的 0.2（地面）与 1.0（飞机）是示例值还是上限？（**决定全部到达时间**）
2. **场景坐标范围多大（米）？** 我们的 100×100 对应实际多少米？（决定 `M_PER_SCENE_UNIT`）
3. **一个规划步对应多少秒？** 或者说，时间窗的单位是什么？（决定 `SEC_PER_STEP`）
4. **是否有电量/载荷/传感器信息？** 说明里完全没有，而我们的能力闸门靠它。
5. **能否提供"到达目标点"的导航模块？** 若下游已有，我们的 `GoalController` 就可以省掉，直接发目标。
6. **位姿话题的发布频率与延迟是多少？** 说明提到 frame 带私有延迟测量信息——我们需要知道量级才能定闭环周期。
7. **`fleet-roster.json` 能否给我们一份？** 我们按号段推的编成需要和它核对。
8. **RTF（仿真/墙钟比）大概多少？** 决定"计划时长"和"实际时长"的偏差有多大。
