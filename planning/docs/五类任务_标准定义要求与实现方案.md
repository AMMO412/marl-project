## 五类任务一揽

| 代号 | 任务 | 空间形态 | 时间形态 | 完成判据的量纲 | 标准判据（一句话） |
| --- | --- | --- | --- | --- | --- |
| `patrol` | 巡逻警戒 | 线 / 环 | 持续、周期 | 时间 | 每个待巡点的**重访间隔**不超过上限 |
| `blockade` | 区域封控 | 面 / 边界 | 持续 | 几何 | **不存在**一条不被覆盖的穿越路径 |

## 1 标准定义与要求

### 1.1 通用要求框架

每一类任务的要求都落在**五个维度**上。这五个维度是后面所有对照的骨架：

| 维度 | 问的问题 | 我们 `contract.py` 里的对应 |
| --- | --- | --- |
| 空间形态 | 目标是点、线、面还是边界？ | `Task.pos`（目前只有点） |
| 时间形态 | 一次到位就算完，还是要维持到窗口结束？ | `Task.window` |
| 协同要求 | `crew` 到底是什么意思？ | `Task.crew` |
| 资源要求 | 要什么载荷、什么传感器、多少续航？ | `need_payload` / `need_sensor` |
| 完成判据 | 量什么？量纲是什么？ | **无对应字段**（目前统一按工作量） |

> 最后一行是全部问题的根源：**判据没有独立字段**，五类共用 `progress / work`。见第 4 节。

### 1.2 `patrol` 巡逻警戒

**定义**：沿规定路线或区域反复巡查，使各处处于持续监视之下，并为其他力量提供预警。

**核心**：这些地方有没有被持续照着——不是"去过没有"。

| 维度 | 要求 |
| --- | --- |
| 空间形态 | 路线（有序航点序列）或区域；**闭环** |
| 时间形态 | 持续、周期；窗口内至少完成规定圈数 |
| 协同要求 | `crew=1` 指**一台负责一条线路**；多机时是并行分管不同线路 |
| 资源要求 | 观察类载荷；续航须支撑整圈 × 圈数 |
| 完成判据 | **最大重访间隔 ≤ 上限**（idleness 型）【我方暂定】 |

**要求要点**：巡逻的重点在"周期性"，因此**重复次数与间隔**比"走完一遍"更重要。

### 1.3 `blockade` 区域封控

**定义**：在指定区域的边界或入口持续占位，切断区域内外的联系，阻止目标进出。

**核心**：有没有一条路能在不被发现的情况下穿过去。

| 维度 | 要求 |
| --- | --- |
| 空间形态 | **面 / 边界**；需要多边形或边界线段，不是点 |
| 时间形态 | 持续；维持到窗口结束或事件驱动解除 |
| 协同要求 | `crew=3` 指**三条互不相交的拦截线**（不是三台并排站）【我方暂定】 |
| 资源要求 | 载荷达标；续航须支撑整个窗口 |
| 完成判据 | **不存在**未覆盖的穿越路径（barrier 型） |

**要求要点**：封控的资源需求随**要求的冗余度**增长，不随区域面积增长——这是它与"区域全覆盖"的根本区别，直接影响 `crew` 该定多少。

### 1.4 `recon` 协同侦察

**定义**：多平台分工对指定区域或目标实施搜索，获取并回传情报，使态势透明化。

**核心**：分头看不同的地方，别两台看同一处。

| 维度 | 要求 |
| --- | --- |
| 空间形态 | 面 / 点；需要覆盖面积的概念 |
| 时间形态 | 有限；到达并覆盖即完成（不要求维持） |
| 协同要求 | `crew=2` 指**分工**，判据看**合并**覆盖，不是各自累加 |
| 资源要求 | 指定传感器（sar）；载荷无要求 |
| 完成判据 | **合并覆盖率 ≥ 阈值**，且**重复覆盖最小** |

**要求要点**：协同在这里的实现方式是**效用去重**——派一台去某处后，该处的剩余价值就下降，第二台自然去别处。

### 1.5 `assault` 机动突击

**定义**：兵力机动到位后，对目标实施急速猛烈的打击，达成毁伤、压制或占领效果。

**核心**：同一个目标可以压多台，不是你一台包一个。

| 维度 | 要求 |
| --- | --- |
| 空间形态 | 点（目标位置） |
| 时间形态 | 瞬时；强调"急速"，窗口窄 |
| 协同要求 | `crew=4` 指**毁伤概率叠加**，不是各摊 1/4 工作量 |
| 资源要求 | 打击类载荷达标 |
| 完成判据 | **毁伤概率 ≥ 阈值**（概率型） |

**要求要点**：多台打同一目标的数学结构是多对一累加，与一对一匹配**不是同一个问题**，不能用同一套求解器。

### 1.6 `hold` 要点坚守

**定义**：对已控制的要点持续保持在位状态，确保在规定时长内不被敌利用。

**核心**：人一离开，那个点的状态就往坏里走。

| 维度 | 要求 |
| --- | --- |
| 空间形态 | 点（要点） |
| 时间形态 | **持续**；必须维持到窗口结束，中途不可撤 |
| 协同要求 | `crew=2` 指**同时在位**的台数；允许轮换 |
| 资源要求 | 观察类载荷；续航须支撑整个窗口 |
| 完成判据 | 窗口内**始终**有 ≥ crew 台在位（区间作业） |

**要求要点**：**"守住"不等于"站上去"**。判据可以写成"该点一定半径内始终有 ≥1 台存活平台"，这样允许轮换与机动防守，比把平台钉死更灵活、也更少制造时序冲突。

## 2 要求汇总

| 要求 | patrol | blockade | recon | assault | hold |
| --- | --- | --- | --- | --- | --- |
| 空间形态 | 线/环 | **面/边界** | **面**/点 | 点 | 点 |
| 时间形态 | 持续 | 持续 | 有限 | 瞬时 | 持续 |
| 中途撤出会怎样 | 该段间隔继续涨 | 出现无覆盖路径 | 已覆盖部分不丢 | — | **立刻失效** |
| `crew` 的数学含义 | 并行线路数 | 拦截线条数 | 分工台数 | 概率叠加兵力包 | 同时在位台数 |
| 载荷要求 | 观察类 | 压制/拦截类 | — | 打击类 | 观察类 |
| 传感器 | eo | 不挑 | **sar** | 不挑 | eo |
| 判据量纲 | 时间 | 几何 | 信息 | 概率 | 状态 |
| 允许轮换 | 是 | 是 | — | — | **是（推荐）** |

## 3 在本项目怎么实现

### 3.1 数据落在哪

| 层 | 文件 | 内容 |
| --- | --- | --- |
| 契约层 | `contract.py` | `TASK_SPECS`（五类模板）、`PLATFORM_SPECS`（四类平台）、`Task` / `Platform` / `Assignment` 数据结构 |
| 规划层 | `planner.py` | 六步：能力过滤 → 代价打分 → 分配求解 → 时序排程 → 冲突消解 → 输出校验 |
| 执行层 | `executor.py` | `StubExecutor`：按计划推进 `progress`，扣电，回传 `Feedback` |
| 驱动层 | `run_flow.py` | 滚动循环、重规划触发、留痕与统计 |

### 3.2 五类当前是怎么被"造出来"和"判完"的

```python
# contract.py —— 五类只有模板参数，没有判据
TASK_SPECS = {
    "patrol":   dict(work=12.0, window=(0, 60), crew=1, need_payload=0.0, need_sensor="eo"),
    "blockade": dict(work=18.0, window=(0, 80), crew=3, need_payload=2.0, need_sensor=None),
    "recon":    dict(work=10.0, window=(0, 50), crew=2, need_payload=0.0, need_sensor="sar"),
    "assault":  dict(work=20.0, window=(0, 90), crew=4, need_payload=4.0, need_sensor=None),
    "hold":     dict(work=15.0, window=(0, 70), crew=2, need_payload=1.0, need_sensor="eo"),
}
```

- **造出来**：`sample_scenario()` 按 `ttypes[j % 5]` 循环取类型，位置随机撒在 100×100 场景里。**五类除了参数不同，结构完全一样**。
- **判完**：`executor.py` 每步 `t.progress += Σ work_rate`，`t.progress >= t.work` 即 `done`。**五类共用这一条**。
- **能力校验**：`planner.feasible()` 已启用续航与载荷；传感器、运动性能**已实现但未启用**（`ENABLED_CHECKS = {"battery", "payload"}`）。
- **分配**：`crew=1` 走匈牙利一对一最优；`crew>1` 按代价排序补位。
- **排程**：`start = max(成员到达时刻)`，`dur = 剩余工作量 ÷ 成员效率和`。
- **消解**：超窗口时依次试 加人 → 换人 → 上报。
- **校验**：第 6 步按开工顺序累加耗电，超续航的**从方案里撤下**。

### 3.3 逐类映射：要求 vs 现状

| 任务 | 要求 | 现状实现 | 满足度 |
| --- | --- | --- | --- |
| `patrol` | 路线 / 周期 / 重访间隔 | 单点 + 工作量累加，**既不是路线也不是间隔** | **不满足** |
| `blockade` | 面/边界 + 无未覆盖穿越路径 | 单点 + 工作量累加；`crew=3` 只是"三台到位" | **不满足**（空间形态级别缺失） |
| `recon` | 合并覆盖率 + 不重复覆盖 | 各自累加；两台飞同一块也算完成 | **不满足** |
| `assault` | 毁伤概率叠加 | 效率求和 → 工期（**线性近似**） | **部分**（形式不同，可用但须声明） |
| `hold` | 窗口内持续在位 | 工作量干完即释放平台 | **不满足** |
| 全部 | 传感器校验（`recon` 要 sar） | 代码已写，**未启用** | **未覆盖** |

## 4 缺口：问题出在一个地方

**所有缺口的根只有一条：五类的完成判据分属五种量纲，而系统里只有一个 `progress / work`。**

这一条派生出三个具体后果：

1. **空间形态被压成了点。** `Task` 只有 `pos`（点），所以"边界""区域""路线"全都表达不了——`blockade` 与 `recon` 的判据因此根本无法计算，不是实现得不好，是**没有输入**。
2. **持续型任务被做成了瞬时型。** `hold` 的判据是"干完 15 个工作量"，平台干完就走；而"坚守"要求它待到最后一步。巡逻同理：干完一遍就完事，没有"再来一遍"。
3. **协同被做成了合力。** `crew>1` 时效率直接求和，于是 `recon` 的两台变成"一起把活干快"，而不是"分头看不同地方"。`assault` 也同理，把概率叠加压成了线性累加。

> 这三条不是 bug，是**模型层面的简化**。写交付文档时必须显式声明，不能让甲方以为五类判据已经各就各位。

## 5 解决方案

### 5.1 总体思路：把判据从"统一工作量"改成"按类型分派"

改动的核心是一个判据分派层，替掉现在 executor 里那一行 `t.progress >= t.work`：

```python
# 【计划】planner/criteria.py
def is_done(t, ctx) -> bool:
    """ctx 携带：每个点/格的最近访问步、平台的在位情况、已覆盖面积、毁伤概率。"""
    if   t.ttype == "patrol":   return max_idleness(t, ctx)   <= PATROL_MAX_IDLE
    elif t.ttype == "blockade": return no_uncovered_path(t, ctx)
    elif t.ttype == "recon":    return union_coverage(t, ctx) >= RECON_COVER
    elif t.ttype == "assault":  return kill_probability(t, ctx) >= ASSAULT_PK
    elif t.ttype == "hold":     return held_until(t, ctx)     >= t.window[1]
```

**`work` 不删，降级为调度参数**（用于估算工期与耗电），完成判定交给判据层。这样排程逻辑不用动，只动判定。

按"要不要甲方先给口径"分成三批，先做不依赖甲方的。

### 5.2 方案 A：V1 内可直接做（不依赖甲方）

| # | 改动 | 落点 | 说明 |
| --- | --- | --- | --- |
| A1 | **`hold` 改成区间作业** | `contract.TASK_SPECS` 加 `until_window_end: True`；executor 判据改"持续到 `window[1]`" | 最小改动、收益最直接。允许轮换：判据写"半径内始终有 ≥1 台"，而不是"某台不动" |
| A2 | **`patrol` 支持路线与圈数** | `Task` 加 `route: List[point]`（默认由 seed 生成 3 个航点【我方暂定】）与 `cycles` | progress 沿航段推进；完成 = 走完 `cycles` 圈。有了路线才谈得上重访间隔 |
| A3 | **`assault` 声明线性近似** | 只改文档，不改代码 | 在 `README` 与交付文档写明："当前按效率求和估算工期，**不是概率模型**，若甲方要求毁伤判据需增补 `p_kill` 字段" |
| A4 | **启用传感器校验** | `planner.ENABLED_CHECKS` 加 `"sensor"` | 代码已写好，加了就生效。风险：`recon` 的候选平台会骤减（只有 `uav_a` 带 sar），需重测完成数——**先测再决定** |

### 5.3 方案 B：需甲方先给口径（口径定了才能动手）

| # | 改动 | 卡在哪 | 甲方要回答什么 |
| --- | --- | --- | --- |
| B1 | **`blockade` 改 barrier 判据** | 需要面/边界几何 | 要"每条穿越路径至少被看一次"（barrier），还是"区域内每处都看得见"（full coverage）？两者资源需求差数倍 |
| B2 | **`recon` 改合并覆盖率判据** | 需要覆盖面积概念 + 去重 | 两台是**分工**还是**合力**？分工才需要判据去重 |
| B3 | **统一 `Task.shape` 字段** | 支撑 B1/B2 | 目标的几何形态由谁给？是点、圆、多边形还是折线 |

> B1/B2 的共同前置是 B3：**给 `Task` 加几何字段**（`point` / `circle` / `polygon` / `polyline`，默认 `point` 向后兼容）。这一条做完，五类判据才都有输入。

### 5.4 方案 C：V2 强化学习（大纲，不在本轮）

- 判据进奖励函数——**奖励函数决定"什么叫好的决策"，须甲方确认**（现见 `spec/SPEC.md` 六之二）。
- 代价函数第 7 维（窗口余量）当前手工三目标一律给 0，这是规划器"短视"的来源。让学习去学这一维的非零权重，比手调更靠谱。
- 巡逻的非确定性（对抗场景下确定性巡逻可被利用）若要支持，需要路线随机化——属 V2。

### 5.5 改动清单与验收

| 批次 | 改动 | 验收方式 |
| --- | --- | --- |
| A1 | `hold` 变区间作业 | 单测：构造 1 个 hold 作业，验证平台**在窗口结束前不被释放**；撤走一台应触发重规划 |
| A2 | `patrol` 路线与圈数 | 单测：`cycles=2` 时完成所需步数约为 `cycles=1` 的两倍 |
| A3 | 文档声明 | 交付文档与 `README` 出现"线性近似、非概率模型"的显式说明 |
| A4 | 启用传感器校验 | `tests/regress.py` 全绿 + 记录启用前后的完成数变化（预期下降） |
| B3 | `Task.shape` | 单测：四种形态的读写与场景文件往返一致 |
| B1/B2 | barrier / 覆盖率判据 | 单测：构造"有一条路没盖住"的场景，判据必须返回未完成 |

**每批做完都要跑** `python tests/regress.py`（期望全绿，含 5 条不变量）与 `python analyze.py --seeds 8`（三类目标分化不退化）。

## 6 待甲方确认（按优先级）

1. **每类任务的完成判据量的是什么？** 时间 / 几何 / 信息 / 概率 / 状态——这一条不定，第 5 节的判据层就落不了地。
2. **封控要 barrier 还是 full coverage？** 决定 `crew` 是 3 还是更多，也决定 15 台够不够。
3. **侦察的两台是分工还是合力？** 决定要不要做去重判据。
4. **持续型任务允许中断多久？** 巡逻/封控/坚守在窗口内允许断多久——这决定轮换能不能做。
5. **突击是否允许抢占在执行的任务？** 允许的话，被打断的作业损失算在哪个优化目标上。
6. **目标的几何形态谁给、什么格式？** 点 / 圆 / 多边形 / 折线。
7. **`crew` 的数值依据。** 3/4/2/2 都是我们自拟，文献只给了结构性解释（拦截线数、概率叠加），没给数字。
