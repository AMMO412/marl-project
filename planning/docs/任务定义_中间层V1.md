## 1 通用作业模型

### 1.1 作业层级

V0.1 采用两级结构：

| 层级 | 说明 | 示例 |
| --- | --- | --- |
| 编组快照 `GroupSnapshot` | 上层一次下发，含全部平台与作业 | version=1 的一次快照 |
| 作业 `Task` | 本层规划对象，可被多台协同 | "T03 突击某点" |
| 指派 `Assignment` | 单个平台可执行的最小单元，即下发件 | "P07 在 t=12 开工" |

暂不引入第三级分解。若后续出现"指派还要再拆成动作序列"（接近、占位、打击、评估），再扩展层级，避免一开始把模型做得过深。

### 1.2 通用字段（作业）

| 字段 | 含义 | 必填 | 示例 |
| --- | --- | --- | --- |
| `tid` | 作业唯一编号 | 是 | `T00` |
| `ttype` | 五类编码之一 | 是 | `patrol` |
| `pos` | 作业点坐标 | 是 | `[70.1, 20.5]` |
| `work` | 总工作量，工作量单位 | 是 | `12` |
| `window` | 时间窗 `[最早开始, 最晚结束]`，步 | 是 | `[0, 60]` |
| `crew` | 需要几台平台协同 | 是 | `1` |
| `need_payload` | 所需载荷 | 是 | `0` |
| `need_sensor` | 所需传感器，null 表示不挑 | 是 | `eo` |
| `progress` | 已完成工作量 | 否（默认 0） | `0` |
| `status` | 作业状态 | 否（默认 `open`） | `open` |

### 1.3 通用字段（平台）

| 字段 | 含义 | 必填 | 示例 |
| --- | --- | --- | --- |
| `pid` | 平台唯一编号 | 是 | `P07` |
| `ptype` | 四类平台之一 | 是 | `uav_a` |
| `pos` | 当前位置 | 是 | `[12.3, 45.6]` |
| `battery` | 剩余续航，**电量单位** | 是 | `60` |
| `payload` | 载荷 | 是 | `2.0` |
| `speed` | 移动速度，距离单位/步 | 是 | `2.0` |
| `work_rate` | 作业效率，工作量单位/步 | 是 | `0.6` |
| `sensor` | 传感器类型 | 是 | `sar` |
| `alive` | 是否在编 | 否（默认 true） | `true` |
| `move_cost` | 移动一步耗电 | 否（**我方暂定**，默认 1.0） | `2.0` |
| `work_cost` | 作业一步耗电 | 否（**我方暂定**，默认 1.0） | `0.36` |

时间单位统一为无量纲"步"，1 步 = 1 个决策周期。坐标系为局部网格 100×100，无量纲。
场景格式 `taskalloc-scenario/v1`，字段级定义见 `spec/SPEC.md` 第三节。

### 1.4 作业状态

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| `open` | 尚未分配平台 | `running` / `failed` |
| `running` | 有平台在推进进度 | `done` / `failed` |
| `done` | 进度达到总工作量 | — |
| `failed` | 执行失败（当前由替身按概率注入） | `open`（释放后重新分配） |

平台侧另有 `alive`，失联即不参与任何分配。单平台回执用 `Feedback.status`：`running` / `done` / `failed` / `idle`。

> 甲方未定义失败与超时的判据。当前**失败=注入事件**、**超时=过了计划 `end` 仍未完成**，均为我方暂定。

### 1.5 编码规则

平台用 P 加两位序号，作业用 T 加两位序号，计划用递增 `plan_id`，编组快照用 `version`。
例如 `P07`、`T03`、`plan_id=12`、`version=3`。编码只用于标识，不承载优先级或类型信息。

## 2 五类作业定义

### 2.1 `patrol` 巡逻警戒

定义：沿指定路线或区域周期巡查，发现并报告异常。

适用条件：有 eo 载荷的平台可用；作业点可定义；时间窗与续航相容。

| 参数 | 类型 | 必填 | 说明 | 默认 |
| --- | --- | --- | --- | --- |
| `work` | float | 是 | 工作量 | 12 |
| `window` | [int,int] | 是 | 时间窗，步 | [0, 60] |
| `crew` | int | 是 | 平台数 | 1 |
| `need_payload` | float | 是 | 所需载荷 | 0 |
| `need_sensor` | enum | 是 | eo | eo |

分解规则：一个作业生成一条指派，crew=1 时一台平台独立承担。该作业走**一对一最优指派**（匈牙利）。

完成判据：`progress >= work`。

主要约束：传感器匹配（**校验已实现，未启用**）、续航、时间窗。

典型输出：巡逻平台编号、开工步、完成步、协同要求 `crew>=1`。

### 2.2 `blockade` 区域封控

定义：对指定区域实施持续占位，控制进出。

适用条件：载荷不低于 2.0 的平台 ≥3 台；区域持续时间已知。

| 参数 | 类型 | 必填 | 说明 | 默认 |
| --- | --- | --- | --- | --- |
| `work` | float | 是 | 工作量 | 18 |
| `window` | [int,int] | 是 | 时间窗，步 | [0, 80] |
| `crew` | int | 是 | 平台数 | 3 |
| `need_payload` | float | 是 | 所需载荷 | 2.0 |
| `need_sensor` | enum | 否 | 不挑 | null |

分解规则：一台作业生成一条**多人指派**，crew=3 时按代价从小到大凑满 3 台（排序补位）。
crew>1 不走匈牙利——一个作业要 N 台已不是一对一，硬套会丢可行解。

完成判据：`progress >= work`。协同效率取成员 `work_rate` 之和。

主要约束：协同人数、载荷、续航、时间窗。人数凑不满时**本轮放弃**；
若可行平台数结构性小于 crew，标记 `need_report` 上报上层。

典型输出：3 台平台编号、统一开工步、完成步、`crew>=3`。

### 2.3 `recon` 协同侦察（自拟）

定义：对指定区域或目标实施侦察，获取并回传情报。

适用条件：带 `sar` 的平台 ≥2 台；目标区可定义。

| 参数 | 类型 | 必填 | 说明 | 默认 |
| --- | --- | --- | --- | --- |
| `work` | float | 是 | 工作量 | 10 |
| `window` | [int,int] | 是 | 时间窗，步 | [0, 50] |
| `crew` | int | 是 | 平台数 | 2 |
| `need_payload` | float | 是 | 所需载荷 | 0 |
| `need_sensor` | enum | 是 | sar | sar |

分解规则：一条多人指派，crew=2。传感器为硬约束，但**当前未启用**（`ENABLED_CHECKS` 只有 battery 与 payload）。

完成判据：`progress >= work`。

主要约束：传感器匹配（未启用）、协同人数、续航、时间窗。

典型输出：2 台 sar 平台编号、开工步、完成步、`crew>=2`。

### 2.4 `assault` 机动突击（自拟）

定义：对指定目标实施接近与打击，达成毁伤、压制或占领效果。

适用条件：载荷不低于 4.0 的平台 ≥4 台；满足最小兵力。

| 参数 | 类型 | 必填 | 说明 | 默认 |
| --- | --- | --- | --- | --- |
| `work` | float | 是 | 工作量 | 20 |
| `window` | [int,int] | 是 | 时间窗，步 | [0, 90] |
| `crew` | int | 是 | 平台数 | 4 |
| `need_payload` | float | 是 | 所需载荷 | 4.0 |
| `need_sensor` | enum | 否 | 不挑 | null |

分解规则：一条多人指派，crew=4，排序补位凑满 4 台。

完成判据：`progress >= work`。**V0.1 不内置毁伤模型。**

主要约束：最小兵力、载荷、续航、时间窗。本层不建模接近路线、攻击阵位与弹药。

典型输出：4 台平台编号、开工步、完成步、`crew>=4`。

### 2.5 `hold` 要点坚守（自拟）

定义：指定平台在要点或阵位持续驻守，保持控制。

适用条件：带 eo 且载荷不低于 1.0 的平台 ≥2 台；坚守时长已知。

| 参数 | 类型 | 必填 | 说明 | 默认 |
| --- | --- | --- | --- | --- |
| `work` | float | 是 | 工作量 | 15 |
| `window` | [int,int] | 是 | 时间窗，步 | [0, 70] |
| `crew` | int | 是 | 平台数 | 2 |
| `need_payload` | float | 是 | 所需载荷 | 1.0 |
| `need_sensor` | enum | 是 | eo | eo |

分解规则：一条多人指派，crew=2。

完成判据：`progress >= work`。平台失联按失败处理并触发重规划。

主要约束：协同人数、载荷、续航、时间窗。

典型输出：2 台平台编号、开工步、完成步、`crew>=2`。

## 3 平台能力与约束

### 3.1 能力项

本层不用 0–3 的离散能力等级，直接用**连续量**——因为代价函数要做加权比较，
离散等级分不出"谁更快一点"。

| 项 | 单位 | 说明 |
| --- | --- | --- |
| `speed` | 距离单位/步 | 移动速度 |
| `work_rate` | 工作量单位/步 | 作业效率 |
| `battery` | 电量单位 | 剩余续航。**不是步数** |
| `payload` | 无量纲 | 载荷 |
| `sensor` | enum | eo / ir / sar |
| `move_cost` | 电量/步 | 移动一步耗电（**我方暂定**） |
| `work_cost` | 电量/步 | 作业一步耗电（**我方暂定**） |

### 3.2 四类平台参数矩阵（占位值）

| 平台类型 | speed | work_rate | battery | payload | sensor | move_cost | work_cost |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `tank` 坦克 | 1.0 | 1.2 | 120 | 8.0 | eo | 0.50 | 1.44 |
| `ugv` 无人战车 | 0.8 | 1.0 | 100 | 6.0 | eo | 0.32 | 1.00 |
| `uav_a` 固定翼A（侦察） | 2.0 | 0.6 | 60 | 2.0 | sar | 2.00 | 0.36 |
| `uav_b` 固定翼B（察打） | 1.6 | 0.5 | 80 | 1.5 | ir | 1.28 | 0.25 |

> 这组数值是**公开近似值**，只为让流程能跑，不是任何真实装备参数。评审时须由甲方确认。

能耗模型（**我方暂定**，WP1 引入）：

```
一次指派的预计耗电 = 移动步数 × move_cost + 作业步数 × work_cost
      move_cost = 0.5 × speed²          move_cost 可 > 1
      work_cost = 1.0 × work_rate²
```

**"跑得快更费电、干得快也更费电"**——这是刻意与完工时间反向的。
第一版把系数定成"快的更省"，结果 energy 与 makespan 永远选同一台平台，
实测 seed0 两个目标成绩单一模一样，区分度为零。物理上那也是反的。

### 3.3 能力匹配规则

能力闸门按以下顺序判断，全部满足才进入候选集：

- 平台在编（`alive`）
- 续航满足：`预计耗电 ≤ 剩余电量`（已启用）
- 载荷满足：`payload ≥ need_payload`（已启用）
- 传感器匹配（**已实现，未启用**）
- 运动性能：`路上时间 ≤ 窗口宽度`（**已实现，未启用**）

能力是硬约束，不能用代价抵消。能力不足的平台不能因为距离近而被选中。
若某作业一个可行平台都没有，**不许静默消失**——必须记入 `rejected` 并进入上报口径。

### 3.4 约束类型

| 类型 | 含义 | 硬/软 | 状态 |
| --- | --- | --- | --- |
| `battery` | 单次指派续航 | 硬 | **已启用** |
| `payload` | 载荷 | 硬 | **已启用** |
| `sensor` | 传感器匹配 | 硬 | 已实现，未启用 |
| `motion` | 运动性能（赶得到） | 硬 | 已实现，未启用 |
| `crew` | 协同最少人数 | 硬 | 已启用 |
| `window` | 时间窗上限 | 硬 | 已启用；消解失败则上报 |
| `horizon` | 规划视野 H | 软 | 已启用；超出则本轮不排 |
| `battery_plan` | 方案级续航叠加 | 硬 | 已启用；第 6 步拦截并撤下 |

> 未启用的两项不进统计的"通过"计数。**未覆盖就是未覆盖，不许计入达标率。**

### 3.5 动态增减

平台失联时：更新平台状态与 `version`；对受影响作业重新过能力闸门、重新分配、重新排时序；
输出计划差异。已下发且未受影响的指派**保持不动**（`KEEP_COMMITMENT`）——
否则每滚一次开工时间就往后挪一次，作业永远做不完，这是滚动时域最常踩的坑。

新增平台只在后续步骤参与分配；已下发的子任务不因新增平台自动重排，避免计划抖动。

**已实现**：`member_lost`（`--kill-at`）。
**仅定格式、未实现**：`member_join` / `objective_switch` / `task_add`。

## 4 规划流程与协同规则

### 4.1 六段流程

```
能力过滤 → 代价打分 → 分配求解 → 时序排程 → 冲突消解 → 输出校验
```

前五段产出方案，第六段**整份方案再过一遍能力约束**——单条指派合法 ≠ 整份方案合法。

### 4.2 指派字段

| 字段 | 类型 | 说明 | 示例 |
| --- | --- | --- | --- |
| `tid` | string | 作业编号 | `T03` |
| `pids` | string[] | 平台编号列表 | `["P02","P05","P09"]` |
| `start` | int | 规划开工步 | `12` |
| `end` | int | 规划完成步 | `26` |
| `seq` | int | 时序序号 | `12` |
| `coord` | string | 协同约束 | `crew>=3` |

### 4.3 规划流程

- 继承上一版已发出的指派（承诺保持）
- 能力过滤：剔除不可行的 (平台, 作业) 组合，记录原因
- 代价打分：按当前优化目标计算每个可行对的代价
- 分配求解：crew=1 走一对一最优指派；crew>1 按代价排序补位
- 时序排程：开工 = 成员到达时刻的最大值；工期 = 剩余工作量 ÷ 成员效率和
- 冲突消解：见 4.7
- 输出校验：按开工顺序逐条累加耗电，超续航的**从方案里撤下**

### 4.4 依赖语义

**V0.1 不实现**作业间依赖（`depends_on` / DAG / 先后关系）。
作业之间当前只通过**抢占同一台平台**间接耦合，没有显式的前置关系。

若后续引入先后关系，贪心与匈牙利都表达不了，须改用约束规划求解器
（评估记录见 `docs/ortools_cpsat_备选.md`，**当前未引入**）。

### 4.5 协同约束

| 约束 | 含义 | 实现 |
| --- | --- | --- |
| `crew>=N` | 最少协同人数 | 人数不足则本轮放弃 |
| 同时开工 | crew>1 时取成员到达时刻最大值 | `start = max(arrive)` |
| 串行错峰 | 同一平台作业区间不重叠 | 后移 `shift` |
| 顺序执行 | 一台平台可接多个作业，按序干 | 排程串行化 |

### 4.6 分配与时序：贪心与最优

不要先把分配和排时序分成两段各算各的。平台做完上一个任务后的位置会改变下一个任务的到达时间，必须一起算。

- 对每个有能力的平台，从它当前位置和 `now` 往后算到达与工期
- 检查时间窗、续航与协同约束
- 计算代价：四项加权和（见 4.10）
- 选代价最小的指派，更新平台时间线

crew=1 的部分额外走**一对一最优指派**（匈牙利，优先 scipy，否则用自带 JV 实现）。
自带一份是必须的：交付环境不支持外网，不能假设目标机装了 scipy/numpy。

最优 vs 贪心对照（`tests/diag_solver.py`，4 seed × 60 步，**已实测**）：

| 平台 × 作业 | 最优合计 | 贪心合计 | 差距 |
| --- | --- | --- | --- |
| 15 × 8（默认） | 1420.0 | 1420.0 | **0.0%** |
| 6 × 8 | 2535.0 | 2571.0 | +1.4% |
| **3 × 8** | 2906.0 | 3134.0 | **+7.8%** |

默认场景差距为 0%——平台远多于 crew=1 的作业，贪心随便挑都不会撞车。
**这不代表求解器没写对，只说明这个场景太宽松。**

### 4.7 冲突类型与消解

| 类型 | 定义 | 消解动作 |
| --- | --- | --- |
| `overlap` | 同一平台在同一时段被分配多个作业 | `shift` 串行后移 |
| `crew_short` | 协同人数凑不满 crew | `defer` 本轮放弃；结构性不足则上报 |
| `window` | 作业无法在时间窗内完成 | `add_crew` → `swap_crew` → `defer` |
| `violation` | 方案级越界：单条合法、叠加超续航 | 拦截，从方案撤下 |

消解动作按固定优先级执行：**加人 → 换人 → 上报**。

为什么必须有"换人"：加人只能缩短**工期**，缩短不了**路上的时间**。
最近的平台赶过去就要 43 步、窗口只剩 30 步时，加多少人都没用，只能换更近的。

硬约束（能力、续航、时间窗上限）不放宽。每个动作记录类型、前后时间、涉及平台与结果。

> **"放弃"本身不是问题，"静默放弃"才是。** 穷尽手段仍无解时标记 `need_report`，
> 由上层决定放宽窗口 / 增派资源 / 正式放弃。中间层不该自己偷偷决定"这个活不干了"。

### 4.8 重规划触发与受影响集合

四类触发源**各自独立计数与留痕**（同一轮可命中多类）：

| 触发源 | 含义 | 状态 |
| --- | --- | --- |
| `member_change` | 成员变化（失联 / 新增） | 已实现（失联） |
| `exec_fail` | 执行失败 | 已实现 |
| `timeout` | 超过计划 `end` 仍未完成 | 已实现 |
| `deviation` | 进度偏差超阈值 | 已实现（阈值 4.0，**我方暂定，未测定**） |
| `periodic` | 滚动周期 K=5 到期 | 已实现 |

为什么要拆开：原来用一个 `reason` 字符串，同一步里同时发生"成员损失 + 执行失败 + 超时"时
**只有最后一个被记下来**，另外两个被吃掉。

受影响集合：占用受影响平台的作业；成员数跌破 crew 的作业。
**不受影响的部分冻结**，输出计划差异而不是整包重发。

### 4.9 "回合"与消解率

**口径未定，本层当前的消解率不能当 2.2（3）的证据。** 三个原因：

- 冲突定义是我们自己定的，不是文档口径
- 每次重规划会把同一件事**重复计数**
- 分母（20 个回合内的检测数）尚无对应的时间基准

建议口径：以"冲突对"为单位计数；同一冲突持续存在时每回合都计入分母，直到解决或明确放弃；
放弃的计入分母、不计入分子。**这三条是我方建议，须甲方确认。**

### 4.10 三类优化目标（2.3（4））

代价是四项加权和（**我方暂定**，`planner.COST_TERMS`）：

| 项 | 含义 |
| --- | --- |
| `time` | 完工所需步数 = 移动步数 + 作业步数 |
| `energy` | 预计耗电 = 移动步数×move_cost + 作业步数×work_cost |
| `spread` | 分散度损失 =（平台到质心距离 − 作业到质心距离）/ 50 |
| `crowd` | 聚集惩罚 = 作业点 30 半径内存活平台数 / 存活平台总数 |

| 目标 | time | energy | spread | crowd | 观测指标 |
| --- | --- | --- | --- | --- | --- |
| `makespan` 任务完成时效 | 1.0 | 0 | 0 | 0 | 完成时刻 |
| `energy` 能耗代价 | 0.3 | 1.0 | 0 | 0 | 每完成作业的能耗 |
| `dispersion` 战场暴露风险 | 1.0 | 0 | 20.0 | 10.0 | 分散度 |

非 1 的两个权重是**扫描出来的，不是拍的**（8 seed × 60 步）：

- `energy.time=0.3`：取 0 时 seed0 一个作业都完不成，完成数只有 makespan 的 36%；取 0.3 回到 79%
- `dispersion.time=1.0`：使 dispersion 完成数与 makespan **持平**（33 vs 33），
  于是"分散度更高"不能再被解释成"干得少所以没聚拢"

> **暴露风险用"分散度"作代理**，不是真实的战场暴露风险。这一点不能含混。

## 附：V0.1 实测基线

> 以下数字全部为**内部相对比较**，只对标自己，不对标文档阈值。
> **证明的是"链路能跑通"，不是"指标已达标"。**

三类目标 × 8 seed × 60 步（15 平台 / 8 作业 / H=20）：

| 目标 | 完成合计 | 完成时刻均值 | 每作业能耗 | 分散度 |
| --- | --- | --- | --- | --- |
| `makespan` | 33 | 35.8 | 31.31 | 36.92 |
| `dispersion` | **33** | 39.5 | 33.89 | **38.59** |
| `energy` | 26 | 34.0 | **25.34** | 37.48 |

- dispersion 分散度 **7/8 seed 胜出，且完成数与 makespan 持平** → 不是"少干活"的假象，**可采信**
- energy 每作业能耗 **7/8 seed 胜出**，但完成数只有 26/33 → **结论要打折**

规划视野 H（6 seed × 60 步）：

| H | 完成数合计 | 消解率均值 | 方案级越界 |
| --- | --- | --- | --- |
| 20（默认） | 24 | 43.4% | 5 |
| 45 | **36** | 64.7% | 22 |

H 大不是没代价：方案级越界从 5 次涨到 22 次。第 6 步会拦截并撤下——
**宁可少干，也不能下发会半路没电的方案。**

已知缺陷「短视」（`tests/test_myopia.py` 可复现，尚未修复）：
贪心会先把"近但不急"的活干掉，把"远但很急"的挤到超时窗，
而先急后缓两个都能成。修法属于 WP1 收尾：代价函数要看得见"后面有多急"。

```bash
python analyze.py --seeds 8        # 三类目标对照表
python tests/diag_solver.py        # 最优 vs 贪心
python tests/regress.py            # 全量回归，期望 18/18
```
